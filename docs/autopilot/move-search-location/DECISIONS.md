# 판단 기록 — 위치를 옮겨 찾기

사람이 자리를 비운 동안 내린 판단을 시간순으로 덧붙인다. 지우지 않는다.

---

## 판단 #1 — worktree를 만든 뒤 로컬 main까지 따라잡혔다
- 상황: worktree 생성 도구의 기본 분기 기준이 `origin/main`인데, 직전에 만든 설계 문서 커밋이 원격에 없어 worktree에 설계 문서가 들어오지 않았다.
- 중요도: 중간
- 확인한 출처: `git remote -v`(원격 있음), `git rev-parse origin/main`(`0e4a093`), 로컬 `HEAD`(`9d3af8a`), `.claude/settings*.json`(worktree 설정 없음 → 기본값 적용)
- 결정: `git merge --ff-only main`으로 따라잡았다. 설정 파일(`worktree.baseRef`)은 건드리지 않았다.
- 근거: 설정을 바꾸면 이 저장소의 앞으로 모든 worktree에 영향을 준다. 이번 작업만의 문제이므로 이번 작업 안에서 해결하는 편이 되돌릴 것이 적다. `--ff-only`를 쓴 것은 새 브랜치에 커밋이 없어 빨리 감기가 보장되고, 만약 아니라면 조용히 병합하는 대신 실패해야 하기 때문이다.

## 판단 #2 — 기존에 깨져 있던 시험을 먼저 고쳤다
- 상황: 코드를 한 줄도 건드리기 전에 돌린 기준선 검증에서 `web/lib/visits.test.ts`의 시험 하나가 실패했다. 내 작업 범위(위치를 옮겨 찾기)와 무관한 기존 결함이다.
- 중요도: 중간
- 확인한 출처: `just check` 출력, 같은 시험을 세 번 돌려 일관되게 실패함을 확인
- 원래 물으려던 것: 범위 밖 결함을 내가 고쳐도 되는가, 아니면 보고만 하고 넘어가야 하는가
- 세운 가정: 고친다. 다만 **원인 진단 없이 시험을 통과시키는 방향으로는 절대 손대지 않는다**는 조건을 붙였다.
- 결정: 원인을 끝까지 추적한 뒤 고치고 별도 커밋으로 분리했다(`86e2f02`).
- 근거: 깨진 시험 위에 새 기능을 쌓으면 이후 실패가 내 변경 때문인지 원래 그랬는지 구분되지 않는다. 별도 커밋으로 둔 것은 되돌리기 단위를 분리해, 나중에 이 수정만 따로 검토하거나 되돌릴 수 있게 하기 위해서다.

## 판단 #3 — 시한폭탄 시험을 인자 명시와 시계 고정 두 가지로 고쳤다
- 상황: 원인은 시험이 `forgetVisit`에 시각 인자를 빠뜨려 실제 시계를 쓴 것이었다. 고치는 방법이 셋이었다.
- 중요도: 중간
- 확인한 출처: `lib/visits.ts` 전문, `lib/visits.test.ts`, 임시 시험 파일로 vitest 4.1.11의 시계 고정이 기본 인자 `new Date()`에 걸리는지 직접 실험(통과 확인 후 삭제)
- 경합 결과: 세 안을 비교했다. ㉮ 그 호출에 인자만 넘긴다 — 최소 변경이지만 같은 사고를 다시 허용한다. ㉯ 시험 파일에 시스템 시계를 고정한다 — 미래의 같은 실수를 막고 제품 코드를 건드리지 않는다. ㉰ 제품 코드에서 `now`의 기본값을 없애 타입 검사로 강제한다 — 가장 강하지만 함수 넷의 인터페이스와 모든 호출부를 바꿔야 해서 이번 작업 범위에서 너무 멀다.
- 결정: ㉮와 ㉯를 함께 넣었다. ㉰는 하지 않았다.
- 근거: 인자를 넘기는 것은 "이 시험은 시각과 무관하다"는 의도를 코드에 드러내는 일이고, 시계 고정은 누군가 인자를 빠뜨렸을 때의 안전망이다. 층위가 달라 중복이 아니다. 실제로 두 방향 변이 시험으로 각각 일하는 것을 확인했다 — 인자를 다시 빼도 통과하고(고정이 일함), 고정까지 빼면 그때 실패한다(진단이 맞음).

## 판단 #4 — 장소 검색 결과를 분류로 거르지 않기로 했다
- 상황: 카카오 장소 이름 검색 결과에 `놀숲 강남역점`(카페) 같은 잡음이 섞인다. 분류 코드로 걸러낼지 정해야 했다.
- 중요도: 중간
- 확인한 출처: 검색어 일곱 개의 실제 응답. `동궁과월지`·`첨성대`·`홍익대학교 정문`·`강남역사거리`는 카카오가 분류를 붙이지 않아 `category_group_name`이 비어 있었다.
- 원래 물으려던 것: 목록이 조금 지저분해지는 것과, 분류 없는 좋은 후보가 사라지는 것 중 무엇이 더 견딜 만한가
- 세운 가정: 거르지 않는 쪽이 낫다고 보았다. 잡음은 상위 다섯 개 중 한두 개 수준이고 그것을 골라도 조회하는 자리가 크게 다르지 않은 반면, 거르면 분류 없는 후보가 통째로 사라진다.
- 결정: 카카오가 주는 순서 그대로 보여준다. 설계 문서 4-3절에 적었다.
- 근거: 걸러내는 기준으로 쓸 수 있는 것이 `category_group_code` 하나인데, 실측에서 좋은 후보의 상당수가 그 값이 비어 있었다. 기준이 잡음과 신호를 가르지 못하면 거르지 않는 편이 낫다.

## 판단 #5 — 새 모듈 이름을 `anchor`로 정했다
- 상황: 조회 기준점의 타입과 검색어 저장을 담을 새 파일 이름이 필요했다.
- 중요도: 낮음
- 확인한 출처: `web/lib/` 기존 파일 이름(pick·places·cuisines·visits·avoid·reasons·api·proxy·geo·errors·radius), `web/app/api/v1/nearby/route.ts`가 읽는 환경변수 `API_ORIGIN`
- 결정: `web/lib/anchor.ts`. `origin`은 쓰지 않는다.
- 근거: 기존 이름이 모두 짧은 명사 하나라 그 관례에 맞춘다. `origin`이 의미상 더 자연스럽지만 이 저장소에 이미 `API_ORIGIN`이 있어 읽는 사람이 두 개념을 헷갈린다.
