## 무엇을 만들었나

**서로 기대는 네 가지를 함께 넣었습니다.** 하나만 넣으면 다른 하나가 망가지는 구조라
따로 뗄 수 없었습니다.

1. **기억** — "여기로 정했어요"를 누른 가게를 브라우저에 적어 두고, 다음에 그 가게를 뺍니다
2. **좁히기** — 카카오의 분류 문자열 대신 우리가 만든 열여덟 가지 음식 종류를 씁니다
3. **넓히기** — 한 지점이 아니라 다섯 지점(중심 + 400m 떨어진 네 점)을 함께 조회합니다
4. **이유** — 왜 이것이 나왔는지 한 줄로 말합니다 (거리·도보 시간·곳 수·무엇을 뺐는지)

2와 3은 **반드시 함께** 가야 합니다. 종류만 잘게 나누고 표본이 45곳이면 카드 절반이
가게 한 곳짜리가 됩니다. 표본을 200곳으로 넓혀야 그 부작용이 사라집니다.

계획에 없던 것 하나를 나중에 더했습니다: **지운 기록 되돌리기**. 디자인 검토가
"기록을 지우면 복구가 없다"를 찾았고, 설계 문서 자신이 컨셉을 "되돌리기 쉬운 버튼"으로
구현한다고 적고 있어 넣기로 했습니다.

## 나중에 더한 것 — 조회 API 접근 제한 (2026-09-07)

배포한 뒤 "API가 외부에서 함부로 접속 못 하게 되어 있느냐"는 물음이 나왔고, **아니었습니다.**
Go 서버의 실서비스 주소가 인터넷에 열려 있어 누구나 조회할 수 있었습니다.

카카오 열쇠 자체는 새지 않습니다(서버 안에만 있고 응답에도 안 실립니다). 문제는 **하루
호출 한도**였습니다 — 조회 한 번이 카카오를 최대 15번 쓰고 한도가 10만 건이라, 약
6,600번이면 그날치가 소진되고 그때부터는 정상 사용자도 전부 실패합니다.

**두 서버가 나눠 갖는 비밀값으로 막았습니다.** Go 서버가 `X-Internal-Key` 헤더를 요구하고,
그 헤더는 브라우저가 아니라 **화면 서버가** 붙입니다. 중계가 서버 쪽에서 일어나므로
개발자 도구에 나타나지 않습니다.

배포한 뒤 실제로 확인했습니다.

| 확인 | 결과 |
|---|---|
| Go 서버 직접 호출 | **401** |
| 화면을 거친 조회 | **200**, 188곳 / 18장 |
| `/healthz` · `/readyz` | 둘 다 **200** (감시 도구가 닿아야 하므로 안 막음) |

**Vercel의 배포 보호로 막으려던 길은 막혔습니다** — 실서비스 주소를 보호하려면 Pro
요금제(월 20달러)가 필요합니다. 공유 비밀값이 같은 결과를 무료로 줍니다.

### ⚠️ 아직 열려 있는 것

**카카오 하루 한도는 여전히 노출돼 있습니다.** 화면 주소의 `/api/v1/nearby`는 누구나
부를 수 있고 한 번에 카카오를 15번 씁니다 — **소진에 필요한 요청 수는 6,600번으로
변하지 않았습니다.** 닫힌 것은 "화면을 거치지 않는 경로" 하나뿐입니다.

닫으려면 Vercel 방화벽의 **요청 빈도 제한**이 필요합니다. 무료 요금제에서도 프로젝트당
규칙 하나를 쓸 수 있고 코드를 고칠 필요가 없지만, 대시보드에서 직접 눌러야 합니다.

## 📌 다음 사람이 알아야 할 것

**1. 통과하는 시험이 아무것도 지키지 않는 경우가 이 저장소에서 열세 번 나왔습니다.**
모양이 늘 같습니다 — **방어 뒤에 또 다른 방어가 있으면, 바깥 방어를 통해 확인하는
시험은 안쪽 방어가 사라져도 초록불입니다.** 예를 들어 `restoreVisits`가 만료 항목을
거르는지를 `readVisits`로 확인하면, `readVisits` 자신이 만료를 거르기 때문에
`restoreVisits`의 방어를 통째로 지워도 통과합니다.

그래서 이 저장소는 **시험을 쓴 뒤 그 방어를 일부러 껐을 때 실제로 실패하는지 확인**하는
것을 절차로 두고 있습니다. 새 시험을 쓰면 이것을 하세요.

**2. 주석의 근거가 코드와 어긋난 것이 여섯 번 나왔습니다.** 동작이 맞아도 이유가 틀리면
그 주석을 믿고 고치는 다음 사람이 잘못 판단합니다. 예: `@theme`을 쓴 이유로 적힌 설명이
실제 Tailwind 동작과 달랐고, 거리 경계값 시험의 주석이 "이 시험이 없으면 분당 거리를
66으로 바꿔도 통과한다"고 했는데 다른 시험이 이미 잡고 있었습니다.

**코드에 관해 쓰기 전에 실제로 확인하세요.** 컴파일해 보거나, 산술로 재 보거나,
변이를 넣어 보면 됩니다.

**3. "안 된다 / 안 들어간다"는 재 본 뒤에만 쓰세요.** 이 작업에서 "16px면 결과 네 줄이
한 화면에 안 들어간다"고 적힌 적이 있는데, 실제 브라우저로 재니 **200px이 남았습니다.**

**4. 화면 시험은 브라우저 없이 돕니다.** `web/vitest.config.mts`가 `environment: "node"`이고
jsdom도 testing-library도 없습니다. **시험할 수 있는 것은 전부 `web/lib/`의 순수 함수로
빼세요.** 화면 조각(`.tsx`)에는 시험이 붙지 않으므로, 거기에 판단 로직을 두면 아무도
지키지 않게 됩니다.

**5. 저장 경계를 넘지 마세요.** 카카오는 **사용자가 직접 정한 가게의 장소 ID와 상호**만
저장을 허용합니다. 응답에서 온 다른 것(분류 문자열, 그것으로 계산한 우리 종류 식별자)은
저장하면 안 됩니다. 그래서 `Visit` 타입에 필드가 셋뿐입니다 — 근거는 설계 문서 9절에
담당자 답변 원문과 함께 있습니다.

`Visit`에 필드를 더하는 것을 타입 검사는 막지 못합니다. `web/lib/visits.test.ts`의
"기록에 음식 종류가 들어가지 않는다"가 유일한 방어입니다.

**6. 서버는 표준 라이브러리만 씁니다.** `api/go.mod`의 의존성 목록이 비어 있어야 합니다.

**7. 올려 둔 곳과 다시 올리는 방법은 `README.md`의 "올려 둔 곳" 절에 있습니다.**
화면과 서버가 각각 Vercel 프로젝트이고 둘 다 서울에서 돕니다.
**push해도 자동 배포되지 않습니다** — Vercel 계정에 GitHub 로그인 연결이 없어
저장소와 잇지 못했습니다. 지금은 `vercel deploy --prod`를 직접 실행해야 합니다.

**환경변수 네 자리가 두 프로젝트에 나뉘어 있고, 그중 `INTERNAL_API_KEY`는
두 곳의 값이 같아야 합니다.** 어긋나면 모든 조회가 401로 막히고, 서버 쪽에만
빠지면 조회 주소가 인터넷에 열린 채로 남습니다.
