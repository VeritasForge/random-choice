### 4-1. 반드시 확인해야 하는 것 하나

**이 서비스의 핵심 규칙이 실제 데이터로 검증되지 않았습니다.**

카카오는 가게마다 분류 문자열을 줍니다. 예: `"음식점 > 한식 > 육류,고기 > 곱창,막창"`. 여기서 앞의 두 단계만 남겨 `"한식 > 육류,고기"`를 음식 종류로 씁니다.

문제는 **카카오가 어떤 가게는 두 단계까지만 분류할 수도 있다**는 점입니다. 그렇다면 `"한식"`과 `"한식 > 육류,고기"`가 서로 다른 두 종류로 갈라지고, 사용자가 `한식` 카드를 골랐을 때 정작 고깃집들은 다른 카드 뒤에 숨습니다. 화면에는 "한식을 골랐는데 식당이 세 곳뿐"으로 보입니다.

이 가능성은 코드 검토에서 지적됐지만, **그 전제를 실제 카카오 응답으로 확인한 사람이 아직 없습니다.** 확인되지 않은 전제로 핵심 규칙을 바꾸면 더 나빠질 수 있어 규칙은 그대로 두었습니다.

### 확인 방법

1. https://developers.kakao.com 에서 애플리케이션을 만들고 REST API 키를 받습니다.
2. `echo 'KAKAO_REST_API_KEY=발급받은키' > api/.env`
3. 서버를 켜고 실제 좌표로 한 번 호출합니다.

```bash
cd api && export $(grep -v '^#' .env | xargs) && go run ./cmd/server &
curl -s "http://localhost:8080/api/v1/nearby?lat=37.4979&lng=127.0276&radius=500" | \
  python3 -c "import json,sys; [print(c['count'], c['name']) for c in json.load(sys.stdin)['cuisines']]"
```

### 결과를 보고 판단할 것

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| `한식`과 `한식 > 육류,고기`가 **함께** 나온다 | 지적이 맞았다 | 규칙을 고쳐야 한다 (아래) |
| 그런 짝이 없다 | 지적이 성립하지 않는다 | 그대로 둔다 |
| 종류가 4개 미만이다 | 후보 화면이 빈약하다 | 기본 반경(500m)을 늘린다 |
| 한 종류에 절반 이상이 몰린다 | 두 단계로도 안 좁혀졌다 | 세 단계를 검토한다 |
| 대부분이 1곳짜리다 | 너무 잘게 쪼갰다 | 한 단계로 줄인다 |

고칠 자리는 `api/internal/cuisine/cuisine.go`의 `maxDepth` 상수 한 줄입니다. 바꾸면 같은 파일의 시험표도 함께 고쳐야 합니다.

## 5. 이미 내려진 결정과 그 이유

되돌릴 수는 있지만, **왜 그렇게 했는지 모르고 되돌리면 같은 문제를 다시 만나게 됩니다.**

| 결정 | 왜 | 어디에 |
|------|-----|--------|
| 장소 정보는 카카오만 쓴다 | 음식 종류를 "돈까스" 수준까지 나눠 주는 곳이 카카오뿐. 구글은 "한식집"까지만 안다 | `api/internal/kakao/` |
| "맛집"이 아니라 "주변 음식점"이라고 쓴다 | 카카오가 평점·리뷰 수를 주지 않아 맛집인지 판단할 근거가 없다. 없는 근거로 맛집이라 쓰면 거짓이 된다 | 화면 문구 전반 |
| 서버에 저장소를 두지 않는다 | 카카오가 결과 저장을 금지한다. 담당자 답변 원문: "실시간 호출로만 이용 가능합니다(Live call only)". 성능 목적 캐싱도 불허 | 서버 전체 — DB·캐시 코드가 아예 없음 |
| 무작위 추첨은 브라우저에서 한다 | 서버에서 뽑으면 "다시 뽑기"마다 카카오를 또 불러야 한다. 다섯 번 누르면 호출이 열다섯 번 나간다 | `web/lib/pick.ts` |
| 요청 값 검사를 열쇠 확인보다 먼저 한다 | 잘못된 요청은 서버 설정과 무관한 호출자의 잘못이라 400이 맞다. 500으로 답하면 책임을 잘못 돌린다 | `api/internal/httpapi/handler.go` |
| 좌표·거리를 못 읽으면 그 가게를 버린다 | 그냥 0으로 두면 거리순 정렬에서 1등이 되어 "가장 가까운 집"으로 표시된다. 0m는 사실이 아니다 | `api/internal/kakao/client.go` |
| 로딩 중에도 버튼을 `disabled`로 만들지 않는다 | `disabled`는 브라우저가 포커스를 떨어뜨려, 키보드·화면 낭독기 사용자가 자기 위치를 잃는다 | `web/components/StartScreen.tsx` |
| 시작 화면을 한 자리에서만 그린다 | 두 자리에서 그리면 React가 화면을 지웠다 새로 만들어, 위 접근성 처리가 무효가 된다 | `web/app/page.tsx` |
| 두 번째·세 번째 페이지가 실패하면 첫 페이지 결과도 버린다 | 일부만 돌려주면 음식 종류 분포가 조용히 치우친다. 무작위로 뽑는 서비스에서는 솔직한 오류가 낫다 | `api/internal/kakao/client.go` |

## 6. 구현이 끝난 뒤 무엇을 검증했나

코드 검토를 세 차례 돌렸습니다. 같은 실수를 반복하지 않도록, 실제로 틀렸던 것들을 적어 둡니다.

**1차에서 드러난 것**
1. **접근성 처리가 무효였다.** 시작 화면을 서로 다른 두 자리에서 그리는 바람에, 로딩이 시작되면 화면이 통째로 새로 만들어져 포커스가 사라졌습니다. 브라우저를 실제로 띄워 재현했고, 고친 뒤에도 브라우저로 확인했습니다.
2. **좌표에 `"NaN"`이 오면 응답 전체가 깨졌다.** 문자열 `"NaN"`이 숫자 변환을 오류 없이 통과하고, 그 값은 JSON으로 표현할 수 없어 인코딩이 실패하는데 그때는 이미 "성공(200)"을 보낸 뒤라 **빈 본문**이 나갔습니다.
3. **시험 두 개가 아무것도 지키지 않았다.** 소스를 일부러 망가뜨려도 시험이 전부 통과했습니다.

**2차에서 드러난 것** — 검토는 세 갈래로 나뉘었습니다.
4. **화면에 막다른 길이 있었다.** 결과가 없어 "2km로 넓히기"를 눌렀는데도 없으면, 화면은 여전히 "1km로 넓히기"(더 좁은 조회)와 "2km로 넓히기"(방금 실패한 것과 같은 조회)만 보여 줬습니다. 두 버튼 모두 반드시 실패합니다.
5. **무작위 추첨을 지키는 시험이 하나도 없었다.** 섞기를 통째로 없애고 앞에서부터 잘라 주는 구현으로 바꿔도 시험이 전부 통과했습니다. 그 상태에서는 어디에서든 늘 같은 종류만 나오는데 화면에도 서버에도 오류가 남지 않습니다.
6. **시험 대상 경로가 `lib`만이라, 그 밖에 넣은 시험은 조용히 무시됐다.** 일부러 실패하도록 만든 시험을 `components/`에 넣어도 "전부 통과"로 초록불이 떴습니다.

**3차에서 드러난 것 — 2차 수정이 만든 회귀입니다. 이것이 가장 중요한 교훈입니다.**
7. **고치면서 새 결함을 만들었다.** 2차에서 "화면이 로딩에 갇히지 않도록" 서버 호출에 20초 상한을 넣었는데, 그 상한이 응답 헤더가 도착하는 순간 풀리도록 잘못 배치돼 있었습니다. 그래서 본문이 중간에 멈추면 화면은 여전히 "주변을 살펴보는 중…"에 영영 갇혔습니다 — 막으려던 바로 그 상태입니다. **고친 자리마다 그 수정을 지키는 시험을 함께 넣어야 하고, 고친 뒤에도 다시 검토해야 한다는 뜻입니다.**
8. **막은 곳을 다른 문으로 다시 열었다.** 카카오 오류의 원인을 로그에 남기려고 응답 본문을 오류 문자열에 실었는데, 카카오 앞에 게이트웨이가 있으면 그 문서에 우리가 보낸 주소(=사용자 좌표)와 헤더(=열쇠)가 되울려 들어옵니다. 바로 그 커밋에서 다른 경로의 좌표 유출을 막아 놓고, 새 경로를 하나 연 셈이었습니다.
9. **운영에서만 쓰는 코드는 시험이 닿지 않는다.** 조회기 생성자가 둘인데 시험은 가짜 서버용만 불렀습니다. 운영용에서 조회 상한을 빠뜨려도 시험은 전부 초록불이었고, 그 상태로 배포하면 모든 조회가 즉시 시간 초과로 끝납니다.

**4차에서 드러난 것**
10. **여러 항목을 한꺼번에 어긋뜨린 시험은 검사 하나만 지켜 준다.** 응답 검사에 항목 다섯 개를 더했는데, 시험 자료가 전부 여러 항목을 동시에 빼는 모양이라 먼저 걸리는 검사 하나가 나머지를 가렸습니다. 검사를 하나만 지워도 시험은 전부 통과했습니다. **온전한 자료를 기준으로 두고 한 항목씩만 어긋뜨려야 각 검사가 실제로 지켜집니다.**

**5차에서 드러난 것**
11. **버튼을 없앴더니 그 버튼을 가리키던 안내 문구가 남았다.** 재시도가 소용없는 오류에서 버튼을 없앴는데, 그 오류들의 안내 문구는 여전히 "처음부터 다시 해 주세요"처럼 화면 안의 행동을 지시하고 있었습니다. 안내를 따르려 해도 누를 것이 없는 상태입니다. 이제 그 규칙(재시도 불가 오류의 안내는 화면 밖에서 할 일만 가리킨다)을 시험이 대조하고, 그 시험이 곧바로 문구 세 개를 잡아냈습니다.
12. **동작을 보는 두 관점이 처음으로 0건을 냈다.** 조용한 실패 관점과 정확성 관점이 아무 지적도 내지 않았습니다.

**6차에서 드러난 것 — 여기서 멈췄습니다.**
13. **검사 기준을 "지금 화면이 쓰는 것"으로 좁히면 화면이 한 줄 늘 때 낡는다.** 응답 원소 검사에서 어떤 항목은 "안 그려도 검사한다", 어떤 항목은 "안 그리므로 검사하지 않는다"고 정반대 근거를 적어 두었습니다. 규칙을 하나로 통일했습니다 — 타입이 약속하는 항목은 전부 확인합니다.
14. **문구를 낱말로 거르는 그물은 우회된다.** "재시도 불가 오류의 안내는 화면 밖 행동만 가리킨다"는 규칙을 낱말 네 개로 대조했는데, 같은 뜻을 다른 말로 쓰면 통과했습니다. 낱말을 보강하고, 그물이 촘촘하지 않다는 사실을 주석에 정직하게 적었습니다.

**멈춘 근거.** 회차별 발견은 40 → 20 → 18 → 12 → 9 → 6건으로 줄었고, 마지막 두 회차에서 동작을 보는 관점들이 0건을 냈습니다. 적대적 검토는 계속 돌리면 언제나 무언가(주석의 뉘앙스, 더 조일 수 있는 검사)를 더 찾아내므로, "발견 0건"이 아니라 **"사용자에게 보이는 동작을 바꾸는 발견이 없음"**을 멈출 기준으로 삼았습니다.

검증이 여기까지 닿지 못한 곳도 적어 둡니다: 화면 조각(`components/`, `app/page.tsx`)에는 자동 시험이 없고(브라우저로 직접 확인했습니다), 실제 카카오 서버를 부르는 경로는 한 번도 실행되지 않았습니다. 왜 그렇게 두었는지는 설계 문서 14절에 적혀 있습니다.

## 8. 손댈 때 알아 둘 것

**서버를 고칠 때.** 표준 라이브러리만 씁니다 — `api/go.mod`의 의존성 목록은 비어 있어야 합니다. 저장소(데이터베이스·캐시·파일)를 추가하면 카카오 이용 정책 위반입니다.

**화면을 고칠 때.** 브라우저 저장소(`localStorage` 등)를 쓰지 않습니다. 같은 이유입니다. 추첨 함수들은 난수 생성기를 인자로 받습니다 — 그래야 시험에서 결과를 예측할 수 있습니다. 새로 부를 때도 `Math.random`을 넘기세요.

```ts
import { pickDistinct, pickAvoiding, pickOne } from "@/lib/pick";

const candidates = pickDistinct(names, 4, Math.random);
const next = pickAvoiding(names, 4, candidates, Math.random);  // 직전 후보를 피해서
const decided = pickOne(candidates, Math.random);              // 보여준 넷 중에서
```

**시험을 돌릴 때.** 실제 카카오를 부르지 않습니다. 서버 쪽은 가짜 HTTP 서버, 화면 쪽은 가짜 `fetch`를 씁니다. 열쇠도 네트워크도 필요 없습니다.

```bash
cd api && go test ./... && go vet ./...
cd ../web && npm run build && npm test && npx tsc --noEmit && npm run lint
```

두 줄을 한 터미널에 붙여 넣으므로 둘째 줄은 `../web`입니다. 그리고 `npm run build`가 `npx tsc --noEmit`보다 앞에 와야 합니다 — 타입 검사에 필요한 것을 Next.js가 빌드하면서 만드는데, 그 결과물은 저장소에 올라가지 않기 때문입니다.

**이 기기에서 주의할 것.** 8080 포트를 관계없는 다른 프로그램이 쓰고 있습니다. 서버를 띄울 때 `PORT=8090`처럼 바꾸고, 화면 쪽에도 `API_ORIGIN=http://localhost:8090`으로 알려 주세요.
