# 조회 범위 넓히기 — 설계 문서

## 1. 한 문단 요약

지금 서비스는 사용자 위치를 포함해 다섯 지점(중심 + 동서남북 400m)을 조회해서
음식점 후보를 모읍니다. 강남역에서 실측하니 이 방식은 실제로 반경 약 560m,
가게 222곳까지만 보고 있었습니다(전체 1,978곳 중 11%). 매일 비슷한 가게만
보인다는 불만의 원인 중 하나입니다. 이번 변경은 조회 지점을 아홉 곳(중심 +
400m 링 4곳 + 800m 링 4곳)으로 늘리고, 그 아홉 곳의 각도를 요청마다 무작위로
돌려서, 호출 한 번(요청 한 건)당 약 123회의 카카오 호출로 강남역 기준 약
61%(1,214곳)까지 보게 만듭니다. "1km 안의 모든 음식점"은 카카오 API 구조상
얻을 수 없다는 것이 실측으로 확인되어 있고(2절), 이번 목표는 그 대신 실현
가능한 최대치까지 넓히는 것입니다.

## 2. 왜 이 변경이 필요한가 — 실측으로 확인한 것

**카카오는 좌표 하나당 최대 45곳까지만 줍니다.** 한 페이지에 15곳까지만
허용하고(그 이상 요청하면 거부됨), 페이지를 3번 넘게 요청해도 3번째와
완전히 같은 15곳을 반복해서 줍니다. 반경을 500m에서 5km로 늘려도 이 45곳은
그대로입니다 — 우리가 조회할 때 정렬 기준을 `sort=distance`(거리순)로
보내고 있고, 카카오는 그 기준으로 가장 가까운 45곳만 내어 주기 때문입니다.
(`sort`는 카카오가 강제하는 값이 아니라 우리가 고르는 파라미터입니다.
왜 거리순만 계속 쓰는지는 3-2절에서 설명합니다.)

**그래서 조회 지점을 여러 곳으로 나눠 각각 45곳씩 받아 합치는 방식(지금
서비스)이 이미 쓰이고 있습니다.** 중심과 동서남북 400m 지점, 다섯 곳입니다.
"400m 떨어진 지점 네 곳"처럼 중심에서 같은 거리에 점을 원 모양으로
늘어놓은 것을 이 문서에서는 **"링"**이라고 부릅니다(자세한 그림은
3-1절에 있습니다). 강남역에서 실측한 결과는 이렇습니다.

| 항목 | 값 |
|---|---|
| 받은 가게 | 222곳 |
| 가장 먼 가게 | 486m |
| 카카오가 세는 반경 1km 안 총 음식점 수 | 1,978곳 |
| **커버리지(받은 곳 ÷ 전체)** | **11%** |

**지점을 늘리고 각도를 돌려 봐도 100%는 구조적으로 안 됩니다.** 지점을
열세 곳(400m 링 4개 + 800m 링 8개)으로 늘리고 각도를 10번 돌려 가며 실측한
결과, 5번째 회전까지는 매번 100곳 넘게 새로 나오다가 6번째부터 3~13곳으로
뚝 떨어져 67~68%에서 멈췄습니다. 게다가 카카오는 "이 반경 안에 몇 곳이
있다"(총 개수)만 알려 줄 뿐 그 목록 자체는 절대 다 주지 않으므로, 정말
빠짐없이 받았는지 확인할 방법이 아예 없습니다. 그래서 이번 설계의 목표는
"전부"가 아니라 **"호출 비용 대비 넓힐 수 있는 만큼"**입니다.

## 3. 무엇을 만드는가

### 3-1. 조회 지점 — 아홉 곳

**"링"이란 중심에서 똑같은 거리에 점을 원 모양으로 늘어놓은 것을
말합니다.** 가락지나 도넛을 떠올리면 됩니다 — 안쪽은 비어 있고, 중심에서
같은 거리인 둘레 위에만 점이 있습니다. 지금 서비스는 사용자 위치(중심)에서
정확히 400m 떨어진 자리에 점 네 개(북·동·남·서)를 찍고 있는데, 이 네 점을
이으면 반지름 400m인 원이 그려집니다. 이것이 **"400m 링"**입니다.

```
사용자 위치(중심)에서 400m 떨어진 네 점을 이으면 이런 원이 그려집니다.

                    ●  (북, 400m)
                 ·      ·
              ·            ·
     (서, 400m)●     ★      ●(동, 400m)      ★ = 사용자 위치(중심)
              ·            ·
                 ·      ·
                    ●  (남, 400m)

  이 네 점 + 그 사이를 잇는 원(점선) 전체를 "400m 링"이라고 부릅니다.
```

**이번 변경은 이 400m 링은 그대로 두고, 800m 떨어진 자리에 점 네 개를
더 찍어 "800m 링"을 하나 더 만듭니다.** 두 링을 겹쳐 그리면 과녁판처럼
중심을 겹겹이 둘러싸는 모양이 됩니다.

```
                        ●  (북, 800m)
                   ·         ·
              ●  (북, 400m)  ·
           ·      ·              ·
        ·      ·                    ·
(서,800m)●   (서,400m)●   ★   (동,400m)●   (동,800m)●
        ·      ·                    ·
           ·      ·              ·
              ●  (남, 400m)  ·
                   ·         ·
                        ●  (남, 800m)

  중심(★, 사용자 위치) + 400m 링(4곳) + 800m 링(4곳) = 조회 지점 아홉 곳
```

800m 링을 8곳이 아니라 4곳으로 줄인 이유는 호출 비용 대비 효율 때문입니다.
같은 조건(강남역, 회전 5회)으로 실측한 결과입니다.

| | 800m 링 8곳 | 800m 링 4곳(채택) |
|---|---|---|
| 요청 1건당 호출(중심 1회만 조회하는 최적화 적용, 3-4절 참고) | 183회 | **123회** |
| 커버리지 | 67% | 61% |
| 하루 처리 가능 요청 수 | 546명 | **813명** |

호출을 33% 줄였는데 커버리지는 6%p만 낮아집니다. 800m 링의 점을 절반으로
줄여도, 회전을 다섯 번 하는 동안 그 네 점이 여러 각도를 돌아가며 대신 채우기
때문입니다. 거리 구간별로 봐도 특정 구간이 뭉텅 비지 않고 고르게 줄었습니다.

### 3-2. 정렬 — 거리순만 쓴다

카카오는 `sort` 값으로 `distance`(거리순)와 `accuracy`(정확도순) 둘 다
받아 줍니다. `accuracy`로 물으면 거리순과는 다른 45곳이 오므로, 이것도
커버리지를 넓히는 손잡이가 될 수 있습니다. 실제로 지난 조사에서 비교한
적이 있습니다(같은 다섯 지점 기준, 회전 없이 한 번만 조회).

| 방법 | 받은 가게 |
|---|---|
| 지점은 그대로 두고 정렬만 `accuracy`를 더 씀 | 295곳 |
| 지점을 아홉 곳으로 늘림(이번 설계) | 572곳 |

**지점을 늘리는 쪽이 정렬을 바꾸는 쪽보다 거의 두 배 더 많은 곳을
찾았습니다.** 그래서 이번 설계는 `accuracy`를 쓰지 않고 `distance`만
유지합니다. `accuracy`를 나중에 더 얹으면 커버리지가 얼마나 더 느는지는
아직 실측하지 않았습니다 — 5절 "확인되지 않은 전제"에 남겨 둡니다.

### 3-3. 회전 — 요청마다 각도를 무작위로 돌린다

400m 링과 800m 링 모두 점이 4개씩이라, 이 배치는 **90도를 돌리면 점들이
서로 자리를 맞바꿔 처음과 같은 모양**이 됩니다(4개 점이 90도 간격이므로).
그래서 완전히 새로운 배치를 볼 수 있는 범위는 0~90도뿐입니다.

**요청이 들어올 때마다 0~90도 사이에서 시작 각도 하나를 무작위로 뽑고,
그 각도에서 18도씩 다섯 걸음(시작각, +18도, +36도, +54도, +72도)만큼
링 전체를 돌려 다섯 번 조회한 뒤 합칩니다.** 시작 각도를 고정하지 않고
매번 무작위로 뽑는 이유는, 고정하면 모든 사용자가 영원히 똑같은 후보
풀에서만 뽑게 되어 "매번 비슷한 가게만 나온다"는 지금 문제가 그대로
남기 때문입니다.

**중심 지점은 회전과 무관하게 딱 한 번만 조회합니다.** 중심은 사용자의
실제 위치이므로 각도를 아무리 돌려도 좌표가 바뀌지 않고, 완전히 같은
좌표로 다시 물으면 완전히 같은 45곳이 돌아온다는 것을 실측으로 이미
확인했습니다. 회전마다 중심을 다시 조회하면 매번 같은 45곳을
헛되이 다시 받는 것이므로, 중심은 요청당 1회, 링 여덟 곳(400m 4 + 800m 4)만
회전마다 다시 조회합니다.

### 3-4. 호출 예산

| 조회 | 횟수 |
|---|---|
| 중심 1곳 × 3페이지 (요청당 1회) | 3회 |
| 링 8곳 × 3페이지 × 회전 5회 | 120회 |
| **합계** | **123회** |

하루 무료 한도 100,000회 ÷ 123회 = **하루 약 813건**의 요청을 처리할 수
있습니다(지금 5지점 방식의 6,666건보다는 훨씬 적지만, 개인 프로젝트 규모
트래픽에는 여유가 있습니다).

병렬로 보내면 강남역 기준 실측 시간은 1.8초 안팎이었습니다(다만 이때는
중심을 낭비 없이 1회만 조회하는 최적화 전 실측이라, 최적화 후에는 이보다
짧아질 것으로 예상합니다 — 정확한 값은 구현 뒤 다시 잽니다). 서버가 이미
가진 조회 전체 시간 상한(12초)과 응답 쓰기 상한(20초)에 여유 있게 들어갑니다.

응답 크기도 함께 늘어납니다 — 강남역 실측 기준 필터 후 가게 수가
188곳에서 1,041곳으로 늘며 JSON 응답이 대략 50KB에서 280KB(비압축)
안팎으로 커집니다. Vercel 함수 응답 한도(4.5MB)에는 한참 못 미치고
전송 구간은 압축되므로 지금은 문제가 아니지만, 다음에 지점을 더
늘릴 때는 함께 확인해야 합니다.

### 3-5. 거리 재계산과 중복 제거 — 지금 코드를 그대로 재사용

두 로직 모두 이미 다섯 지점 조회에 구현되어 있고, 지점 수만 늘어날 뿐
방식은 바뀌지 않습니다.

- **거리 재계산**: 옮긴 지점으로 조회하면 카카오가 그 지점 기준 거리를
  주는데, 그대로 쓰면 사용자에게 실제보다 훨씬 가깝다고 보여 주게 됩니다
  (기존 실측에서 17배 차이가 난 사례가 있습니다). 그래서 모든 가게의 거리를
  좌표로 다시 계산해 **사용자 원래 위치 기준**으로 바꿉니다.
- **중복 제거**: 여러 지점의 조회 범위가 겹치면 같은 가게가 여러 번
  나올 수 있으므로, 가게 식별자로 걸러 한 번만 남깁니다. 식별자가 빈
  가게는 판정할 수 없으므로 그대로 살려 둡니다(기존 정책 유지).

## 4. 함께 고쳐야 하는 것 — "반경 넓히기" 안내 문구와 그 예외

지금 화면에는 결과가 없을 때 "1km로 넓히기" · "2km로 넓히기" 버튼이
있습니다(`web/lib/radius.ts`의 `widerThan`). 이번 변경 이후에는
**음식점이 빽빽한 곳에서는 그 숫자가 결과에 영향을 주지 않습니다** —
카카오에 보내는 반경 값은 `sort=distance` 정렬에서, 한 지점 주변에
45곳 넘게 있을 때만 결과와 무관해지기 때문입니다.

**다만 이 무관함은 조건부입니다.** 45곳을 못 채우는 드문 지역(예:
README에 기록된 제주 애월 사례)에서는 반경을 넓히면 실제로 각 지점이
더 먼 가게까지 받아 옵니다. 빈 결과 화면은 정의상 바로 이런 지역에서만
뜨므로, 그 화면의 `다시 찾아보기` 버튼만은 반경을 2km(`WIDER_RADIUS`)로
한 단계 넓혀 다시 조회합니다. 평소 조회(시작 화면, 결과가 있을 때의
재조회)는 여전히 기본 반경(500m)만 쓰고, 다시 눌러도 새 결과가 나오는
진짜 이유는 회전 각도가 매번 새로 뽑히기 때문입니다.

문구는 두 경우 모두 반경 숫자를 사용자에게 노출하지 않습니다 —
"1km로 넓히기" 같은 옛 문구 대신 "다시 찾아보기" 하나로 통일합니다.

## 5. 확인되지 않은 전제 — 사람이 판단해야 하는 것

1. **모든 수치가 강남역 한 곳에서만 측정됐습니다.** 음식점이 드문 지역에서는
   애초에 45곳을 못 채워 이 문제가 아예 없거나, 반대로 아홉 지점을 다 써도
   부족할 수 있습니다. 다른 성격의 지역(예: 상권이 작은 동네)에서 재측정이
   필요합니다.
2. **429(카카오 호출 한도 초과) 반응이 하루 누적 초과인지 순간 호출 제한인지
   여전히 확인되지 않았습니다.** 이번 조사 과정에서 800회 넘는 호출을 짧은
   시간에 병렬로 보냈는데 한 번도 429가 뜨지 않았다는 정황은 있지만, 이것이
   실제 서비스의 동시 사용자 여러 명이 겹칠 때도 안전하다는 증거는 아닙니다.
3. **회전 시작 각도를 뽑는 정확한 방법(난수 범위, 시드)은 구현 단계에서
   정합니다.** 이 문서는 "0~90도에서 무작위로 하나, 거기서 18도씩 다섯
   걸음"이라는 방식만 정합니다.
4. **이 문서의 커버리지 수치는 카카오 원본 응답(음식점 분류 `FD6` 전체)
   기준이지, 서비스가 술집 등을 걸러낸 뒤의 순수 점심 후보 기준이 아닙니다.**
   같은 강남역 조건으로 배포된 서비스에 직접 물어보면(걸러진 뒤) 188곳이
   나오는데, 이 문서 2절의 "222곳"은 그 필터를 적용하기 전 원본 값입니다.
   실제 사용자가 보게 되는 순수 후보 수는 이 문서의 수치보다 조금 더
   적을 것입니다. 다만 필터가 지점 수·회전 여부와 무관하게 비슷한 비율로
   깎아 낼 것으로 보이므로, **옵션 사이의 상대적 비교(61% vs 11%)는 유효할
   가능성이 높습니다** — 이것도 구현 뒤 필터 적용 후 수치로 다시 확인해야
   합니다.
5. **`sort=accuracy`를 이번 아홉 지점 + 회전 방식에 추가로 얹으면 커버리지가
   얼마나 더 느는지 재 보지 않았습니다.** 3-2절의 295곳 vs 572곳 비교는
   회전 없이 지점 하나만 바꿔 본 결과라, 지금 채택한 방식(9지점 + 회전
   5회) 위에 `accuracy`까지 더하면 어떻게 되는지는 별도로 확인해야 합니다.

## 6. 완료 조건

- [x] 조회가 아홉 지점(중심 1 + 400m 링 4 + 800m 링 4)을 조회하고, 중심은
      요청당 정확히 1회만 조회한다(회전 횟수와 무관) — `api/internal/kakao/client.go`의
      `SearchAround`에서 중심(`SearchRestaurants`)을 회전 루프 밖에서 한 번만 부르고,
      링 점(`ringPoints`)만 회전 루프 안에서 반복 생성하는 것으로 확인
- [x] 링 여덟 곳의 각도가 요청마다 무작위로 정해진 시작각을 기준으로
      18도씩 다섯 걸음 돌아간다 — `startRad := c.randFloat() * rotationRangeDeg * ...`로
      시작각을 뽑고, `rotationSteps=5`·`rotationStepDeg=18.0`으로 다섯 걸음 도는 것을 코드로 확인
- [x] 모든 가게의 거리가 사용자 원래 좌표 기준으로 재계산된다 — `geo.DistanceMeters(lat, lng, ...)`로
      확인(3-5절과 동일하게 기존 로직 재사용)
- [x] 중복 가게가 제거되고, 식별자가 빈 가게는 그대로 남는다 — `seen` 맵으로 ID 중복만 거르고,
      빈 ID는 그대로 통과시키는 것을 코드로 확인
- [x] 조회 전체가 서버의 시간 상한(12초) 안에 끝난다 — 2026-09-20 로컬 실측(강남역 좌표)에서
      실제 응답 시간은 0.43초였다
- [x] "다시 찾아보기" 문구가 반경 숫자를 언급하지 않도록 바뀐다 — `web/app/page.tsx`의
      빈 결과 안내 버튼 문구가 "다시 찾아보기"로 바뀌어 있음을 확인
- [x] `just check`가 통과한다(서버 시험·검사, 화면 빌드·시험·타입·린트) — 2026-09-20 실행,
      종료 코드 0
- [x] 강남역급 밀집 지역에서 재측정했을 때 커버리지(이 문서와 같은 기준 —
      술집 등을 거르기 전, 카카오 원본 응답 기준)가 55~65% 범위 안에
      들어온다(정확히 61%가 아니어도 됨 — 카카오 응답이 그사이 바뀔 수 있음) —
      2026-09-20 로컬 실측. `/api/v1/nearby`는 이미 걸러낸 뒤의 값(1,041곳)만
      주므로, 필터 전 원본 값을 직접 재려고 `kakao.Client.SearchAround`를
      부르는 임시 확인용 프로그램을 만들어 강남역 좌표로 돌렸다(커밋하지
      않고 확인 후 지웠다) — **원본 1,221곳.** 같은 날 카카오에 직접 물은
      반경 1km 총 개수는 1,979곳이었다. **커버리지 = 1,221 ÷ 1,979 = 61.7%,
      목표 범위(55~65%) 안이고 이 문서 1절이 예측한 61%와도 거의 일치한다.**
      (재현 방법: `kakao.NewClient(key).SearchAround(ctx, lat, lng, 500)`을
      직접 호출해 `len(places)`를 세면 필터 전 원본 값을 다시 잴 수 있다.)

## 7. 어떻게 시험하는가

- **가짜 카카오 서버**로 지점 수·중심 재조회 여부·회전 각도 적용을 확인한다
  (지금 다섯 지점 조회를 시험하는 방식과 같은 패턴을 아홉 지점 + 회전으로
  확장한다).
- **거리 재계산·중복 제거**는 기존 시험이 이미 다루고 있으므로, 지점 수가
  늘어난 것에 맞춰 표본만 키운다.
- **실제 카카오 응답으로 하는 확인**은 이 문서의 실측처럼 개발자가 수동으로
  한 번 재현해 커버리지가 기대 범위 안에 있는지 확인한다(자동화된 시험으로
  만들지 않는다 — 카카오 응답 자체가 매번 조금씩 바뀔 수 있어 고정된 기대값을
  둘 수 없기 때문).
