# 맛집 기록 — 설계 문서

## 1. 한 문단 요약

지금 이 서비스는 `여기로 정했어요`를 누른 가게를 14일 동안 추첨에서 빼는 데만 기록을
씁니다. 다녀와서 맛있었던 곳을 모아 두고 다시 찾아갈 방법은 없습니다. 이번 변경은
다녀온 가게를 **맛집으로 저장**하고, 먹은 메뉴와 한 줄 메모를 적고, **지역 → 음식
유형 → 식당** 순서로 모아 보는 화면을 더합니다. 저장을 잊지 않도록 다음 날 시작
화면이 "어제 가신 곳, 맛있었나요?"라고 한 번만 조용히 묻습니다. 이번 작업은 로그인
없이 브라우저 저장소(`localStorage`)만으로 동작하며, 나중에 로그인을 붙일 때 저장
위치만 바꿔 끼울 수 있게 저장소의 모양을 처음부터 정해 둡니다.

## 2. 왜 이 기능이 필요한가

**아는 맛집으로 가는 길이 없습니다.** 이 서비스는 "뭘 먹을지 모를 때" 새로운 곳을
권하는 데 맞춰져 있습니다. 그런데 점심을 고르는 사람은 "지난번 그 돈까스집"처럼
이미 아는 곳을 떠올리고 싶을 때도 많습니다. 지금은 방문 기록이 14일 뒤 사라지고,
그 안에서도 "맛있었는지"를 남길 자리가 없습니다.

**추첨과 역할을 나눕니다.** 맛집을 추첨에 강하게 섞으면 매번 같은 곳이 나와 "새로
권한다"는 성격이 흐려집니다. 그래서 아는 곳은 맛집 화면이 맡고, 추첨은 지금처럼
새로운 곳을 권하며, 우연히 뜬 가게가 맛집이면 표시만 붙입니다.

## 3. 이미 정한 것과 그 이유

| 주제 | 정한 것 | 이유 |
|---|---|---|
| 추첨과의 관계 | 결과 화면에 우연히 뜬 맛집에 `맛있었던 곳` 표시만 붙인다. 뽑힐 확률은 바꾸지 않는다 | 아는 곳으로 가는 길은 맛집 화면이 맡는다 |
| 14일 회피 | 맛집도 다녀온 지 14일 안이면 추첨에서 뺀다 | 회피의 목적("같은 집만 가지 않게")을 유지한다. 가고 싶으면 맛집 화면에서 찾는다 |
| 맛집 화면 구조 | 지역 → 음식 유형 → 식당 | 사용자 요청 |
| 분류를 채우는 사람 | 사용자가 직접 고른다. 지역은 그 가게를 찾을 때 기준이던 장소 이름으로 미리 채우고, 음식 유형은 기본값 없이 고른다 | 카카오가 저장을 허용하지 않는 값(주소·좌표·분류 문자열)으로 자동 분류할 수 없다(5절) |
| 저장하는 자리 | 결과 화면에는 버튼을 더하지 않고, 방문 기록에서 지정한다 | 결과 화면은 가장 빡빡한 경우 이미 휴대폰 한 화면을 14px 넘는다(`web/components/ResultScreen.tsx` 주석, 2026-09-07 실측) |
| 저장을 권하는 방식 | 시작 화면에 조용한 카드 하나. 정한 다음 날부터, 한 번에 한 곳, 같은 가게는 한 번만 묻는다 | 점심 직전에 앱을 여는 사람을 막지 않는다 |
| 분류 입력 시점 | 시작 화면 카드에서는 한 번 눌러 바로 저장하고, `지금 분류하기`를 작게 붙인다. 분류하지 않은 맛집은 `분류 안 됨`에 둔다 | 저장이 가벼워야 권하는 것이 성공한다 |
| 맛집 한 곳에 적는 것 | 맛있었던 메뉴 이름 여러 개와 한 줄 메모. 둘 다 선택 | 다음 방문에 쓸모 있는 만큼만 받는다. 메뉴별 평가는 리뷰 앱에 가까워져 뺐다 |
| 로그인 없이 | 모든 기능이 브라우저 저장소로 동작한다 | 로그인 전에 기능을 써 보게 한다 |

## 4. 구조

### 4-1. 무엇이 어디에 생기나

```
 web/app/page.tsx (화면 이동)
   ├─ StartScreen ────── 유도 카드                          (추가)
   ├─ VisitsScreen ───── 가게마다 [맛있었어요]               (추가)
   ├─ ResultScreen ───── 맛집이면 `맛있었던 곳` 표시          (추가)
   ├─ FavoriteForm ───── 지역·음식 유형·메뉴·메모 입력        (새 화면)
   └─ FavoritesScreen ── 지역 → 음식 유형 → 식당              (새 화면)
            │
            ▼
 web/lib/favorites.ts ── FavoritesRepo (저장소 모양) ◀── 화면은 이것만 안다
            ├─ 브라우저 구현 (localStorage)       ← 이번 작업
            └─ 계정 구현 (Go 서버 → DB)           ← 로그인 작업에서 끼운다

 api/ ── GET /api/v1/cuisines                              (추가)
         음식 유형 18가지를 돌려준다. 카카오를 부르지 않는다
```

### 4-2. 저장소 모양

로그인 작업에서 DB 구현을 끼울 때 화면을 고치지 않도록, 처음부터 **비동기(Promise)**로
정합니다. 브라우저 구현은 즉시 끝나지만 DB 구현은 네트워크를 거치기 때문입니다.

```ts
type Favorite = {
  placeId: string;          // 카카오 장소ID      ─┐
  placeName: string;        // 상호                ├ 카카오가 저장을 허용한 셋
  placeUrl: string;         // 카카오 place_url   ─┘ 비어 올 수 있다
  region: string | null;    // 사용자가 쓴 지역. null이면 `분류 안 됨`
  cuisineId: string | null; // 사용자가 18가지 중 고른 유형. null이면 `분류 안 됨`
  menus: string[];          // 맛있었던 메뉴 이름
  memo: string;             // 한 줄 메모
  savedAt: string;          // ISO 8601. 우리가 만든 값
};

interface FavoritesRepo {
  list(): Promise<Favorite[]>;
  save(favorite: Favorite): Promise<void>; // 같은 placeId면 덮어쓴다. 실패하면 reject
  remove(placeId: string): Promise<void>;
}
```

"고친 시각"은 두지 않습니다. 로그인할 때 브라우저 기록과 계정 기록이 겹치면 계정 쪽을
따르기로 했으므로(8절) 시각을 비교할 일이 없습니다.

### 4-3. 방문 기록에 두 칸을 더한다

기록 화면에서 `맛있었어요`를 누르면 링크와 지역 기본값이 있어야 하는데, 지금 `Visit`
(`web/lib/visits.ts`)에는 장소ID·상호·날짜뿐입니다.

| 더할 칸 | 무엇 | 저장해도 되는 이유 |
|---|---|---|
| `placeUrl` | 카카오 상세 링크 | 카카오가 허용한 셋 중 하나다. 지금은 담지 않고 있을 뿐이다 |
| `spotName` | 그 가게를 찾을 때 기준이던 장소 이름. 현재 위치로 찾았으면 빈 문자열 | 사용자가 고른 장소의 상호라, 이미 저장하는 `random-choice.last-spot.v1`과 같은 근거다 |

`visits.ts` 주석은 "Visit에 담을 수 있는 것은 카카오 약관이 정한 것"이라고 강조하는데,
두 칸은 그 원칙 안에 있으므로 주석을 함께 고칩니다. 두 칸이 없는 옛 기록은 빈 문자열로
읽습니다. 열쇠(`random-choice.visits.v1`)는 바꾸지 않습니다. 옛 값을 새 의미로 잘못
읽는 일이 없고, 칸이 비어 있을 뿐이기 때문입니다.

### 4-4. 음식 유형 목록을 Go 서버에서 받는다

지금 18가지 목록은 Go 서버(`api/internal/cuisine/cuisine.go`)에만 있고, 화면은 조회
결과에 나온 종류만 받습니다. 분류 입력 화면이 18가지 전부를 보여 주려면 목록이 필요합니다.
화면 쪽에 목록을 복사해 두면 Go에서 종류를 고칠 때 화면이 조용히 어긋나므로, Go 서버에
`GET /api/v1/cuisines`를 더하고 화면 서버에는 기존 두 경로(`nearby`, `places`)와 같은
방식의 중계 경로를 둡니다. 이 경로는 카카오를 부르지 않으므로 호출 한도와 무관합니다.

### 4-5. 새 저장 열쇠

| 열쇠 | 담는 것 |
|---|---|
| `random-choice.favorites.v1` | 맛집 목록 |
| `random-choice.asked.v1` | 시작 화면 카드로 이미 물어본 장소ID. 방문 기록에서 사라진 ID는 함께 지운다 |

## 5. 무엇을 저장하고 무엇을 저장하지 않는가

카카오 로컬 API는 응답 저장을 금지하고, 예외로 "사용자가 직접 찜하거나 담은 장소의
장소ID·상호·place_url"만 허용합니다(담당자 답변 원문은
`docs/superpowers/specs/2026-09-06-lunch-upgrade-design.md` 9절).

| 저장한다 | 근거 | 저장하지 않는다 |
|---|---|---|
| 장소ID·상호·place_url | 카카오가 허용한 셋 | 좌표, 거리, 주소, 전화번호 |
| 지역, 메뉴, 메모 | 사용자가 쓴 글이라 카카오 응답이 아니다 | 카카오 분류 문자열 |
| 음식 유형 | **사용자가 우리 18가지 목록에서 직접 고른 값** | 결과 화면에서 계산된 종류를 자동으로 넣은 값 |

**셋째 줄이 이 설계에서 가장 조심할 경계입니다.** 사용자가 결과 화면에서 이미
`돈까스·우동`을 골랐으니 분류 입력 화면에 그 값을 미리 채우면 편합니다. 하지만 그 값은
카카오 분류 문자열로 계산한 것이라 "응답에 기반한 가공 데이터"로 읽힐 여지가 있고,
카카오가 이 구조를 승인한 사례는 아직 없습니다. 그래서 카카오에 문의하고(부록),
허락을 받기 전까지는 **기본값 없이 사용자가 고르게** 합니다. 이 이유를 코드 주석에도
적어, 나중에 편의로 기본값을 넣지 않게 합니다.

## 6. 화면 흐름

### 6-1. 전체 이동

```
 ① 시작 ──[맛있었어요]──▶ (바로 저장) ──[지금 분류하기]──▶ 분류 입력 ──▶ ① 시작
   │ └──[맛집 보기]─────────────────────────────────────▶ 맛집 화면
   │                                                        │ [고치기]
   └──[최근 기록 보기]──▶ ⑤ 기록 ──[맛있었어요]──▶ 분류 입력 ──▶ ⑤ 기록
                                                             ▲
                          맛집 화면 ──[고치기]────────────────┘ (돌아가면 맛집 화면)
```

분류 입력 화면의 `돌아가기`는 **들어온 화면으로** 돌아갑니다. 검색 화면의 `돌아가기`를
직전 화면으로 가게 고친 것(커밋 `18b1207`)과 같은 규칙입니다.

### 6-2. 시작 화면: 카드는 제목과 버튼 사이의 빈 공간에 둔다

시작 화면은 주요 버튼을 화면 맨 아래에 붙여 둡니다. 코드 주석의 근거는 "한 손 그립이
49%, 전체 터치의 75%가 엄지"(Hoober 2013)입니다. 이 배치에서 카드를 버튼 아래에 넣으면
버튼 묶음이 카드 높이만큼 위로 밀려, 늘 누르던 자리에 다른 것이 오게 됩니다. 그래서
카드는 **제목과 버튼 사이의 늘어나는 빈 공간**에 둡니다.

```
┌──────────────────────────────────────┐
│           오늘은 뭐 먹지?             │  ← 위쪽: 늘어나는 빈 공간
│  주변에 있는 음식점을 보고 ...        │
│ ┌──────────────────────────────────┐ │
│ │ 어제 가신 연돈, 맛있었나요?       │ │  ← 카드
│ │ [ 맛있었어요 ]  [ 괜찮아요 ]  ✕  │ │
│ └──────────────────────────────────┘ │
│                                      │
│  [ 첨성대로 다시 찾기 ]              │  ← 아래쪽: 버튼 위치 그대로
│  [ 지금 있는 곳에서 찾기 ]           │
│  [ 다른 곳에서 찾기 ]                │
│   최근 기록 보기 · 맛집 보기          │  ← 링크 둘을 한 줄에
└──────────────────────────────────────┘
```

`맛집 보기`를 새 버튼 한 줄로 더해도 버튼 묶음이 위로 자라므로, 지금의 `최근 기록 보기`
링크와 한 줄에 나란히 둡니다.

### 6-3. 시작 화면 카드의 규칙

| 규칙 | 내용 |
|---|---|
| 누구를 묻나 | 방문 기록 가운데 ① 정한 날이 오늘보다 앞이고(브라우저 기준 날짜), ② 아직 묻지 않았고, ③ 맛집이 아닌 곳. 여럿이면 가장 최근 것 하나만 |
| `맛있었어요` | 바로 맛집으로 저장한다. 지역은 그 방문의 `spotName`(비었으면 `null`), 음식 유형은 `null`. 저장에 성공하면 그 장소ID를 `asked`에도 적는다(적지 않으면 나중에 맛집에서 뺐을 때 같은 가게를 다시 묻는다). 카드가 "맛집에 담았어요 · 지금 분류하기"로 바뀐다 |
| `괜찮아요` / ✕ | 카드를 닫고 그 장소ID를 `asked`에 적는다 |
| 다시 묻나 | 답하든 닫든 같은 가게는 다시 묻지 않는다. 방문 기록이 14일 뒤 사라지면 물을 대상에서도 빠진다 |
| 포커스 | 카드가 나타나도 포커스를 옮기지 않는다 |

"정한 날이 오늘보다 앞"으로 두는 이유는, 정하고 몇 분 뒤 앱을 다시 열면 아직 먹기 전일
수 있기 때문입니다.

### 6-4. 기록 화면

가게 줄마다 지금의 `지우기` 옆에 `맛있었어요`를 더합니다. 누르면 분류 입력 화면으로 바로
갑니다. 기록 화면은 여유가 있을 때 여는 곳이라 시작 화면처럼 "일단 저장"할 필요가 적습니다.
이미 맛집인 가게는 버튼 대신 `맛집` 글자를 보여 줍니다. 결과 화면이 이미 정한 가게에 버튼
대신 `정하신 곳`을 보여 주는 것과 같은 방식입니다.

### 6-5. 분류 입력 화면

```
  연돈
  지역       [ 첨성대        ]   이전에 쓴 지역: [경주] [회사 근처]
  음식 유형  [ 고르기 ▼      ]   (18가지)
  메뉴       [ 등심카츠 ✕ ] [ 치즈카츠 ✕ ]  [ + 메뉴 추가 ]
  메모       [ 줄이 김, 11시 반 전에 가기     ]
  [ 저장 ]   [ 돌아가기 ]
  맛집에서 빼기                     ← 이미 맛집인 가게를 고칠 때만
```

지역은 글자로 받되, 예전에 쓴 지역을 단추로 보여 줘서 `경주`와 `경주시`처럼 같은 곳이
두 칸으로 갈라지는 일을 줄입니다.

| 칸 | 상한 | 넘으면 |
|---|---|---|
| 지역 | 20자 | 입력 칸이 더 받지 않는다 |
| 메뉴 이름 | 20자, 한 가게에 10개 | 같다 / 10개가 되면 `+ 메뉴 추가`를 감춘다 |
| 메모 | 100자 | 같다 |

상한의 근거는 "휴대폰 한 줄에 들어가는 정도"라는 감각뿐입니다. 이 서비스에는 계측이 없어
이 값을 고칠 자료도 모이지 않습니다.

### 6-6. 맛집 화면

```
  맛집
  분류 안 됨 (2)          ← 맨 위: 채울 것이 있으면 먼저 보이게
    연돈                                   [고치기]

```

- 지역과 음식 유형은 가나다순, 식당은 저장한 순서의 역순(최근 것이 위)으로 둡니다.
- 지역만 있고 음식 유형이 없는 가게(또는 그 반대)도 `분류 안 됨`에 둡니다. 두 칸이 모두
  있어야 제자리에 들어갑니다.
- 상호는 카카오 상세 링크입니다. 링크가 비어 있으면 글자만 보여 줍니다.
  결과 화면(`PlaceRow`)과 같은 이유입니다.
- 맛집이 하나도 없으면 "다녀온 곳을 기록에서 맛집으로 담을 수 있어요"라고 안내합니다.

### 6-7. 결과 화면

맛집인 가게는 둘째 줄 맨 앞에 `맛있었던 곳 · 120m · 도보 2분 · ...`처럼 붙입니다. 새 줄을
만들지 않는 이유는 6-2와 3절에 적은 결과 화면의 높이 여유 때문입니다.

## 7. 오류 처리

**맛집 저장 실패는 조용히 넘기지 않습니다.** 방문 기록은 저장이 실패하면 조용히
포기합니다(`visits.ts`의 `save`). 방문 기록은 버튼 한 번이라 잃어도 손실이 작지만, 맛집에는
사용자가 직접 쓴 메뉴와 메모가 들어 있어 말없이 사라지면 신뢰를 잃습니다.

| 상황 | 동작 |
|---|---|
| 저장 실패(용량 초과, 저장이 막힌 브라우저 등) | 입력 화면에 "저장하지 못했어요"를 띄우고 입력한 내용을 그대로 둔다 |
| 시작 화면 카드에서 저장 실패 | 카드에 같은 안내를 띄우고, `asked`에는 적지 않는다(다음에 다시 물을 수 있게) |
| 저장된 값 일부가 망가짐 | 항목별로 걸러 나머지는 살린다(`visits.ts`와 같은 방식) |
| 음식 유형 목록 조회 실패 | 음식 유형 칸만 "불러오지 못했어요 · 다시 시도"로 두고 나머지 칸은 쓸 수 있게 한다. 음식 유형 없이 저장하면 `분류 안 됨`으로 들어간다 |
| 목록에 없는 `cuisineId`가 저장돼 있음(Go에서 종류를 없앤 경우) | 맛집 화면에서 `분류 안 됨`으로 보여 준다. 저장된 값은 지우지 않는다 |

## 8. 로그인 작업이 들어올 자리

로그인과 계정 저장소는 다음 설계 문서에서 따로 다룹니다. 이번 작업은 아래 약속만 지킵니다.

- 화면은 `FavoritesRepo`만 알고, 계정 구현을 끼울 때 화면을 고치지 않는다.
- 로그인할 때 브라우저 기록과 계정 기록은 `placeId`를 기준으로 합치고, 겹치면 계정 쪽을
  따른다.
- `asked`(물어본 장소ID)는 계정으로 옮기지 않는다. 기기마다 한 번씩 물어도 해가 적고,
  옮길 칸을 줄이는 편이 낫다.

그 작업에서 이미 정한 것은 아래와 같습니다. 다음 설계 문서를 쓸 때 출발점으로 삼습니다.

| 주제 | 정한 것 |
|---|---|
| 로그인 수단 | 카카오와 네이버. 네이버는 정식 오픈 전에 네이버의 사전 검수(2~3 영업일, 반려되면 다시)를 거쳐야 하고, 그 전에는 등록된 테스터만 로그인할 수 있다 |
| 받는 정보 | 각 서비스의 사용자 식별번호만. 닉네임·이메일은 받지 않는다. 카카오 계정과 네이버 계정은 별개 계정으로 다룬다 |
| 인증을 맡는 곳 | Go 서버. 화면 서버(Next.js)는 지금처럼 중계만 하고 로그인 쿠키를 그대로 넘긴다 |
| 인증 라이브러리 | `zitadel/oidc`의 rp 패키지로 OIDC 로그인을 처리하고, 쿠키 처리기를 반드시 설정한다(설정하지 않으면 state를 비교하지 않는다) |
| 세션 | 무작위 세션 ID를 쿠키에 담고 DB의 세션 표에서 찾는다. 로그아웃하면 서버에서 세션을 지운다 |
| DB | Vercel Marketplace로 만드는 Neon PostgreSQL, 싱가포르 리전. `api` 프로젝트의 실서비스 환경에만 연결하고, 미리보기 배포마다 DB 브랜치를 만드는 기능은 켜지 않는다. 리전은 만든 뒤 바꿀 수 없다 |
| 로그인할 때 | 브라우저의 맛집·방문 기록·설정을 계정에 올리고 브라우저에서 지운다 |
| 로그인 중 | 계정만 읽고 쓴다 |
| 로그아웃하면 | 브라우저는 빈 둘러보기 상태가 된다(공용 PC에 기록이 남지 않게) |
| 따라다니는 설정 | "최근에 정한 곳 빼기" 스위치와 마지막으로 고른 장소 이름 두 가지 |
| DB가 안 될 때 | 추첨은 계속된다. 로그인 사용자의 방문 기록을 읽지 못하면 회피 없이 추첨하고 화면에 알린다 |

## 9. 시험과 확인

| 대상 | 방식 |
|---|---|
| 저장소(`favorites.ts`) | `visits.ts`처럼 가짜 저장소를 넣어 node에서 시험한다 |
| 시작 화면 카드의 대상 고르기, 맛집 화면의 묶기·정렬 | 날짜와 목록을 받는 순수 함수로 떼어 시험한다. `pick.ts`가 난수를 밖에서 받는 것과 같은 방식이다 |
| `Visit` 두 칸 추가 | 두 칸이 없는 옛 기록을 읽어도 망가지지 않는지 시험한다 |
| Go 음식 유형 목록 경로 | 기존 `handler_test.go` 방식으로 18가지가 빠짐없이 나오는지, 카카오를 부르지 않는지 시험한다 |

**방어를 지키는 시험은 그 방어를 껐을 때 실제로 실패하는지 확인합니다.** 예를 들어 "한 번
물은 가게는 다시 묻지 않는다" 시험은 `asked`를 확인하는 줄을 지운 채 돌려 빨간불이 나는지
봅니다.

화면(React 컴포넌트)은 이 저장소에 컴포넌트 시험이 없으므로 이번에도 두지 않고, 실제
브라우저에서 휴대폰 폭(390×844)으로 아래 흐름을 직접 확인합니다.

1. 어제 날짜의 방문 기록이 있을 때 시작 화면에 카드가 뜨고, **카드가 있을 때와 없을 때
   버튼 묶음의 위치가 같다.**
2. 카드의 `맛있었어요` → `지금 분류하기` → 저장 → 시작 화면으로 돌아온다.
3. 기록 화면의 `맛있었어요` → 분류 입력 → 저장 → 기록 화면에 `맛집` 글자가 보인다.
4. 맛집 화면에서 `분류 안 됨`이 맨 위에 있고, 분류를 채우면 제자리로 옮겨 간다.
5. 결과 화면에서 맛집인 가게의 둘째 줄이 `맛있었던 곳 · `으로 시작한다.
