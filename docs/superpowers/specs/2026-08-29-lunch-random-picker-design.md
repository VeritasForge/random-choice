# 점심 결정 서비스 — 설계 문서

작성일: 2026-08-29

---

## 1. 무엇을 만드는가

점심에 무엇을 먹을지 대신 정해 주는 웹 서비스다. 사용자는 위치만 허용하면 되고, 후보를 직접 입력하지 않는다. 서비스가 사용자 주변에 실제로 있는 음식점들을 보고, 거기서 **음식 종류**(한식·분식·돈까스 같은 것)를 추려 몇 개만 제시한다. 그중에서도 못 고르면 버튼 하나로 하나를 확정해 준다. 종류가 정해지면 그제서야 그 종류를 파는 주변 가게 목록을 보여준다.

핵심은 **"어디 갈지"보다 "뭘 먹을지"를 먼저 좁힌다**는 점이다. 가게 이름 20개를 늘어놓으면 사람은 여전히 고르지 못한다. "오늘은 돈까스"라고 한 단계만 정해 주면 나머지는 쉬워진다.

## 2. 왜 이렇게 만드는가

결정을 못 하는 이유는 선택지가 없어서가 아니라 **너무 많아서**다. 그래서 이 서비스는 선택지를 늘리지 않고 줄이는 방향으로만 동작한다.

- 후보를 직접 입력하게 하지 않는다 — 입력 자체가 또 하나의 결정이다.
- 한 번에 3~4개만 보여준다 — 그 이상은 다시 고민이 된다.
- 마지막에는 사람이 아니라 서비스가 정한다 — "못 고르겠어" 버튼이 존재 이유다.

## 3. 사용자가 겪는 흐름

화면은 세 개다.

```
 화면 1 — 시작                화면 2 — 후보 고르기            화면 3 — 결과
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│  오늘 점심,       │      │ 어느 쪽이 끌리나요?│      │   오늘은 → 돈까스 │
│  제가 정해 드릴게요│  →   │ ┌────┐┌────┐    │  →   │                  │
│                  │      │ │한식││분식│    │      │ 주변 돈까스집 4곳  │
│  [ 위치 허용하고  │      │ └────┘└────┘    │      │ · 연돈      120m │
│    시작하기 ]    │      │ ┌────┐┌────┐    │      │ · 홍대돈까스 240m │
│                  │      │ │돈까스││국밥│   │      │ · ...            │
│                  │      │ └────┘└────┘    │      │                  │
│                  │      │ [다시 뽑기]      │      │ [처음부터 다시]   │
│                  │      │ [못 고르겠어 →]  │      │                  │
└──────────────────┘      └──────────────────┘      └──────────────────┘
```

- **화면 1**: 위치 권한을 요청한다. 허용하면 곧바로 주변을 조회한다.
- **화면 2**: 주변에 실제로 존재하는 음식 종류 중 4개를 무작위로 뽑아 카드로 보여준다. 카드를 누르면 그 종류로 확정된다. `다시 뽑기`를 누르면 다른 4개가 나온다. `못 고르겠어`를 누르면 그 4개 중 하나가 무작위로 확정된다.
- **화면 3**: 확정된 종류와, 그 종류에 해당하는 주변 가게 목록을 가까운 순으로 보여준다. 각 가게는 카카오맵 상세 페이지로 연결된다.

## 4. 장소 데이터를 어디서 가져오는가

### 4.1 조사한 것과 결론

주변 음식점 정보를 주는 곳으로 카카오 로컬, 구글 Places, 네이버 지역검색 세 곳을 공식 문서와 운영사 답변으로 확인했다. 결론은 **카카오 로컬 하나만 쓴다**이다.

| 기준 | 카카오 로컬 | 구글 Places (New) | 네이버 지역검색 |
|------|-------------|-------------------|-----------------|
| 음식 종류를 얼마나 잘게 나눠 주나 | `음식점 > 한식 > 육류,고기 > 곱창,막창` 처럼 4단계까지 | `korean_restaurant`, `chinese_restaurant` 처럼 나라 단위까지만. 분식·돈까스·국밥에 해당하는 값이 없다 | 분류를 주지만 형태 확인 못 함 |
| 좌표와 반경으로 주변 검색 | 된다. 반경 0~20,000m | 된다 | 안 된다. 검색어 기반만 |
| 한 번에 받을 수 있는 개수 | 최대 45개 | 요청당 최대 20개 | 최대 5개 |
| 평점·리뷰 수 | 주지 않는다 | 준다 | 주지 않는다 |
| 서버에서 호출 가능 | 된다 (`Authorization: KakaoAK <키>`) | 된다 | 된다 |
| 결과를 저장·캐싱해도 되나 | **안 된다** | 장소 식별자만 무기한, 나머지는 제한 | 확인 못 함 |
| 카카오맵/구글맵이 아닌 화면에 표시 | 제한하지 않는다 | 지도에 표시하려면 반드시 구글 지도 위여야 한다 | 확인 못 함 |
| 출처 표기 의무 | 없다 | 있다 | 확인 못 함 |

**카카오를 고른 이유는 하나다.** 이 서비스는 "음식 종류를 뽑는" 서비스인데, 그 재료를 가진 곳이 카카오뿐이다. 구글은 "한식집"까지만 알고 "돈까스집"은 모른다. 구글의 평점이 아무리 좋아도, 종류를 못 나누면 이 서비스는 성립하지 않는다.

### 4.2 이 선택이 만드는 제약 두 가지

**첫째, 이번 버전에서 "맛집"은 만들 수 없다.**

원래 구상은 "주변 맛집을 우선 보여준다"였다. 그런데 카카오는 평점도 리뷰 수도 주지 않는다. 맛집인지 아닌지 판단할 근거 자체가 없다는 뜻이다. 없는 근거로 "맛집"이라고 표시하면 거짓말이 된다.

그래서 이번 버전의 기준은 **가까운 순**이고, 화면 문구도 "주변 맛집"이 아니라 "주변 음식점"으로 쓴다. 평점을 붙이는 일은 이번 범위 밖이며, 11절에 다음에 할 일로 적어 두었다.

**둘째, 서버에 어떤 저장소도 두지 않는다.**

카카오 담당자는 성능 개선 목적의 캐싱까지 명시적으로 금지했다. 원문은 이렇다.

> "사용자 요청 빈도를 줄여 응답 속도 개선 목적이라면 사실 임시 DB 역할로 볼 수 있는데요. 이는 운영 정책에 위반한 것으로 허용되지 않으며, 로컬API의 실시간 호출로만 이용 가능합니다. (Live call only)"

20분짜리 임시 저장을 물은 다른 문의에도 "REST API는 실시간 호출로만 사용 가능하며 위와 같은 '임시 저장' 형태의 사용은 허용하지 않습니다"라고 답했다.

따라서 이 서비스에는 데이터베이스도, 서버 메모리 캐시도, 파일 저장도 두지 않는다. 서버는 요청을 받으면 그 자리에서 카카오를 호출하고, 가공해서 돌려주고, 아무것도 남기지 않는다.

이 제약은 오히려 구조를 단순하게 만든다. 저장소가 없으면 저장소를 다루는 코드도, 만료 처리도, 정합성 문제도 없다.

### 5.1 Go 서버는 왜 필요한가

브라우저에서 카카오를 직접 부르면 서버 없이도 동작한다. 그런데도 서버를 두는 이유는 두 가지다.

1. **열쇠를 숨기기 위해.** 카카오 호출에는 비밀 열쇠(REST API 키)가 필요하다. 브라우저 코드에 넣으면 누구나 개발자 도구로 꺼내 쓸 수 있고, 그러면 남의 호출량이 내 한도를 갉아먹는다. 서버가 대신 부르면 열쇠는 서버에만 있다.
2. **분류 문자열을 다듬기 위해.** 카카오가 주는 `음식점 > 한식 > 육류,고기 > 곱창,막창` 같은 문자열을 사람이 볼 만한 음식 종류로 바꾸고 개수를 세는 일이 필요하다. 이 규칙은 앞으로 계속 손볼 곳이라, 화면 코드가 아니라 시험하기 쉬운 서버 쪽에 둔다.

### 5.2 폴더 구조

```
random-choice/

│   ├── app/
│   │   ├── page.tsx            화면 1~3을 담는 한 페이지

│   ├── lib/
│   │   ├── api.ts              Go 서버 호출
│   │   └── pick.ts             무작위 추출 (순수 함수, 시험 대상)
│   └── package.json
│
└── api/                        Go 서버
    ├── cmd/server/main.go      실행 진입점
    ├── internal/
    │   ├── kakao/              카카오 호출 담당
    │   ├── cuisine/            분류 문자열 → 음식 종류 변환 (순수 로직)
    │   └── httpapi/            요청 처리
    └── go.mod
```

각 폴더가 하는 일을 한 줄로 말할 수 있어야 한다는 기준으로 나눴다.

- `kakao` — 카카오와 말이 통하게 하는 곳. 바깥 세상과 닿는 유일한 지점.
- `cuisine` — 문자열을 음식 종류로 바꾸는 곳. 바깥과 닿지 않아 시험하기 가장 쉽다.
- `httpapi` — 두 곳을 이어 붙이고 화면이 요청한 형태로 돌려주는 곳.

## 6. 서버가 제공하는 기능

기능은 하나뿐이다.

```
GET /api/v1/nearby?lat=37.4979&lng=127.0276&radius=500
```

| 값 | 뜻 | 규칙 |
|----|----|------|
| `lat` | 위도 | 필수. -90 ~ 90 |
| `lng` | 경도 | 필수. -180 ~ 180 |
| `radius` | 반경(미터) | 선택. 기본 500. 최소 100, 최대 20000 |

성공하면 이렇게 답한다.

```json
{
  "cuisines": [
    { "name": "한식 > 육류,고기", "count": 7 },
    { "name": "분식",            "count": 5 },
    { "name": "일식 > 돈까스",    "count": 3 }
  ],
  "places": [
    {
      "id": "26338954",
      "name": "연돈",
      "cuisine": "일식 > 돈까스",
      "distance": 120,
      "roadAddress": "서울 강남구 테헤란로 123",
      "phone": "02-000-0000",
      "placeUrl": "http://place.map.kakao.com/26338954",
      "lat": 37.4981,
      "lng": 127.0281
    }
  ]
}
```

- `cuisines`는 개수가 많은 순으로 정렬해 보낸다. 무작위로 뽑는 것은 화면이 한다.
- `places`는 가까운 순으로 정렬해 보낸다.
- 각 가게의 `cuisine`은 `cuisines`의 `name` 중 하나와 반드시 일치한다. 화면은 이 값으로 걸러 낸다.

실패하면 상태 코드와 함께 이렇게 답한다.

```json
{ "error": "invalid_coordinates", "message": "위도·경도 값이 올바르지 않습니다." }
```

| 상황 | 상태 코드 | `error` 값 |
|------|-----------|-----------|
| 위경도가 없거나 범위를 벗어남 | 400 | `invalid_coordinates` |
| 반경이 범위를 벗어남 | 400 | `invalid_radius` |
| 카카오 열쇠가 설정되지 않음 | 500 | `not_configured` |
| 카카오가 오류를 돌려줌 | 502 | `upstream_error` |
| 카카오 호출 한도 초과 | 429 | `quota_exceeded` |
| 주변에 음식점이 하나도 없음 | 200 | (오류 아님. 빈 배열을 돌려준다) |

주변에 아무것도 없는 것은 오류가 아니다. 빈 결과를 정상으로 돌려주고, 화면이 "반경을 넓혀 보세요"라고 안내한다.

## 7. 음식 종류를 뽑아내는 규칙

이 서비스에서 가장 중요한 규칙이다.

카카오는 가게마다 `category_name`이라는 문자열을 준다. 형태는 이렇다.

```
"음식점 > 한식 > 육류,고기 > 곱창,막창"
"음식점 > 분식"
"음식점 > 일식 > 돈까스"
```

여기서 음식 종류를 만드는 규칙은 다음과 같다.

1. `>` 로 자르고 각 조각의 앞뒤 공백을 없앤다.
2. 맨 앞 조각이 `음식점`이면 버린다. (`음식점`은 모든 가게에 공통이라 정보가 없다)
3. 남은 조각 중 **앞에서 최대 2개**를 다시 ` > ` 로 이어 붙인다.
4. 남은 조각이 하나도 없으면 그 가게는 결과에서 제외한다.

적용하면 이렇게 된다.

| 카카오가 준 값 | 만들어지는 음식 종류 |
|----------------|---------------------|
| `음식점 > 한식 > 육류,고기 > 곱창,막창` | `한식 > 육류,고기` |
| `음식점 > 분식` | `분식` |
| `음식점 > 일식 > 돈까스` | `일식 > 돈까스` |
| `음식점 > 중식 > 중국요리` | `중식 > 중국요리` |
| `음식점` | (제외) |

**왜 2개인가.** 1개만 쓰면 `한식`·`중식` 수준이라 여전히 안 좁혀진다. 주변 음식점의 절반이 `한식`으로 묶여서, 그게 뽑혀도 사용자는 다시 고민한다. 3개 이상 쓰면 `한식 > 육류,고기 > 곱창,막창`처럼 너무 잘게 쪼개져서 후보 카드가 죄다 1곳짜리가 된다. 2개가 "돈까스", "분식", "고깃집" 같은 사람의 말에 가장 가깝다.

**확인이 필요한 부분.** 위 예시 중 `음식점 > 일식 > 돈까스`와 `음식점 > 중식 > 중국요리`는 카카오가 실제로 그렇게 준다고 확인한 값이 아니라, 확인된 형태(`음식점 > 한식 > 육류,고기 > 곱창,막창`)에서 미루어 쓴 것이다. 실제 열쇠로 한 번 호출해 실제 분포를 본 뒤, 2단계가 맞는지 다시 판단한다. 이 확인 작업은 구현 계획에 별도 항목으로 넣는다.

**특히 이 실패 모드를 확인해야 한다 — 코드 리뷰에서 지적된 것이다.** 카카오가 어떤 가게는 2단계까지만(`음식점 > 한식`), 다른 가게는 3~4단계까지(`음식점 > 한식 > 육류,고기 > 곱창,막창`) 분류한다면, 위 규칙은 이 둘을 `한식`과 `한식 > 육류,고기`라는 **서로 다른 두 종류로 갈라 놓는다.** 그러면 사용자가 `한식` 카드를 골랐을 때 2단계까지만 분류된 가게만 보이고, 정작 고깃집들은 다른 카드 뒤에 숨는다. 사용자 눈에는 "한식을 골랐는데 식당이 세 곳밖에 없다"로 보인다.

이 지적의 전제 — "카카오가 일부 가게를 2단계까지만 분류한다" — 는 **아직 실제 데이터로 확인되지 않았다.** 지적의 근거로 쓰인 것은 이 저장소의 시험용 가짜 데이터였다. 확인되지 않은 전제 위에서 규칙을 바꾸면 더 나빠질 수 있으므로 규칙은 그대로 두었다. 열쇠를 받으면 **가장 먼저** 이것을 확인한다: 실제 응답에 `음식점 > XX` 형태(2단계)와 `음식점 > XX > YY...` 형태(3단계 이상)가 **같은 XX 아래에 함께** 나오는가. 나온다면 규칙을 고쳐야 하고, 안 나온다면 이 지적은 성립하지 않는다.

## 8. 무작위 추첨을 어디서 하는가

**브라우저에서 한다.** 서버가 아니다.

이유는 `다시 뽑기` 때문이다. 추첨을 서버에서 하면 다시 뽑을 때마다 카카오를 또 불러야 한다. 사용자가 다섯 번 다시 뽑으면 카카오 호출이 열다섯 번(3페이지 × 5회) 나간다. 한도를 빠르게 갉아먹고, 매번 기다림이 생긴다.

브라우저가 한 번 받은 목록을 화면 상태로 들고 있다가 거기서 뽑으면, 다시 뽑기는 즉시 끝나고 추가 호출이 없다.

**이것이 캐싱 금지에 걸리지 않는 이유.** 카카오가 금지한 것은 서버가 결과를 저장해 두었다가 **다른 요청에 재사용**하는 것이다. 지금 화면에 띄워 둔 결과를 사용자가 조작하는 동안 브라우저 메모리에 들고 있는 것은 "한 번의 실시간 호출 결과를 표시하는 중"이며, 새로고침하면 사라진다. 서버에도 브라우저 저장소에도 아무것도 남기지 않는다. 이를 확실히 하기 위해 **브라우저 저장소(localStorage·sessionStorage·쿠키)에 장소 정보를 쓰지 않는다**를 규칙으로 못 박는다.

추첨 규칙:

- 후보는 4개. 음식 종류가 4개보다 적으면 있는 만큼만 보여준다.
- 같은 종류가 후보에 두 번 나오지 않는다.
- 개수가 많은 종류가 더 잘 뽑히게 하지 않는다. 모든 종류가 같은 확률이다. 가중치를 주면 흔한 한식만 계속 나와서 서비스의 재미가 사라진다.
- `다시 뽑기`는 직전 후보 4개와 최대한 겹치지 않게 뽑는다. 남은 종류가 부족하면 겹쳐도 된다.

추첨 함수는 난수 생성기를 밖에서 주입받는 순수 함수로 만든다. 그래야 시험할 때 정해진 난수를 넣어 결과를 예측할 수 있다.

## 9. 오류 상황과 대응

| 상황 | 화면이 하는 일 |
|------|---------------|
| 사용자가 위치 권한을 거부함 | "위치를 알아야 주변 음식점을 찾을 수 있어요"라고 안내하고 다시 시도 버튼을 준다. 브라우저 설정에서 권한을 켜는 방법도 한 줄로 알려준다 |
| 위치를 가져오는 데 실패함(신호 없음 등) | 같은 안내 + 다시 시도 |
| 주변에 음식점이 없음 | "반경 500m 안에 음식점이 없어요. 넓혀 볼까요?" + 1km/2km 버튼 |
| 서버가 응답하지 않음 | "잠시 후 다시 시도해 주세요" + 다시 시도 버튼 |
| 카카오 한도 초과 | "오늘 조회 한도를 다 썼어요. 내일 다시 이용해 주세요" |

권한 거부는 오류가 아니라 정상적인 선택지로 다룬다. 위협하거나 반복해서 권한을 요구하지 않는다.

## 10. 어떻게 시험하는가

시험은 바깥 세상에 닿지 않는 것부터 만든다.

**Go 서버**

1. `cuisine` — 분류 문자열을 음식 종류로 바꾸는 규칙. 7절의 표를 그대로 시험 표로 옮긴다. 빈 문자열, `음식점`만 있는 경우, 공백이 이상한 경우, `>`가 없는 경우를 모두 넣는다. 바깥과 닿지 않으므로 가장 먼저 만든다.
2. `kakao` — 카카오를 실제로 부르지 않는다. Go 표준 라이브러리의 시험용 HTTP 서버를 띄워 미리 준비한 응답을 주게 하고, 그것을 제대로 해석하는지 본다. 3페이지를 이어 붙이는 동작, 마지막 페이지 표시가 왔을 때 멈추는 동작, 카카오가 오류를 줬을 때의 동작을 각각 시험한다.
3. `httpapi` — 진짜 카카오 대신 가짜 조회기를 끼워 넣고, 6절의 요청·응답 규칙과 오류 표가 그대로 지켜지는지 본다.

**화면**

4. `pick.ts` — 8절의 추첨 규칙. 정해진 난수를 주입해 결과를 예측 가능하게 만들고, 4개보다 적을 때·중복이 없는지·다시 뽑기가 겹치지 않는지를 시험한다.

**실제 열쇠가 있어야만 할 수 있는 확인** (사람이 직접 한다)

5. 실제 좌표로 서버를 한 번 호출해, 7절의 2단계 규칙이 실제 데이터에서 말이 되는지 눈으로 본다.

시험은 실제 카카오를 부르지 않는다. 그래야 열쇠 없이도, 네트워크 없이도 항상 같은 결과로 돌아간다.

## 11. 이번 범위에서 뺀 것

일부러 뺐다. 나중에 필요해지면 그때 각각 별도 계획으로 다룬다.

| 뺀 것 | 왜 뺐나 |
|-------|---------|
| 평점 기반 "맛집" 정렬 | 카카오가 평점을 주지 않는다. 붙이려면 구글을 함께 써야 하는데, 가게를 서로 짝지어야 하고 비용과 표시 의무가 붙는다. 이것만으로 계획 하나 분량이다 |
| 지도 표시 | 목록과 카카오맵 링크로 충분하다. 지도를 넣으면 지도 라이브러리, 마커, 화면 크기 대응이 따라온다 |
| 여러 명이 함께 고르기 | 서버에 상태를 둬야 하는데 지금 구조에는 저장소가 없다. 구조가 바뀌는 일이라 따로 다룬다 |
| 최근에 먹은 것 제외 | 무엇을 먹었는지 기록해야 하고, 기록은 저장이다. 브라우저 저장소를 쓸 수는 있으나 이번 범위를 넘는다 |
| 로그인·계정 | 필요 없다. 위치만 있으면 동작한다 |
| 주소를 직접 입력해 위치 지정 | 위치 권한 거부 시의 대안으로 유용하나, 주소를 좌표로 바꾸는 기능이 추가로 필요하다 |
| 저녁·카페 등 다른 상황 | 점심 하나를 제대로 만드는 것이 먼저다 |

## 12. 완료 조건

아래가 모두 참이면 이 설계의 구현이 끝난 것이다. 각 항목은 명령 한 줄로 확인할 수 있어야 한다.

1. `cd api && go build ./...` 가 오류 없이 끝난다.
2. `cd api && go test ./...` 가 전부 통과한다. `cuisine`·`kakao`·`httpapi` 세 곳 모두 시험이 있다.
3. `cd api && go vet ./...` 가 아무것도 지적하지 않는다.
4. `cd web && npm run build` 가 오류 없이 끝난다.
5. `cd web && npm test` 가 전부 통과한다. 추첨 규칙 시험이 포함된다.
6. `cd web && npx tsc --noEmit` 가 타입 오류를 내지 않는다.
7. 열쇠 없이 서버를 켜고 `/api/v1/nearby?lat=37.5&lng=127.0` 를 호출하면 500과 `not_configured` 가 돌아온다. (열쇠가 없어도 서버가 죽지 않는다)
8. 잘못된 좌표(`lat=999`)를 호출하면 400과 `invalid_coordinates` 가 돌아온다.
9. 저장소를 쓰는 코드가 없다. `grep -rn "localStorage\|sessionStorage\|database/sql\|redis" api/ web/app web/lib web/components` 결과가 비어 있다.
10. 진짜 열쇠가 소스 코드에 들어 있지 않다. 아래 명령의 출력이 비어 있다.
    ```bash
    grep -rn "KakaoAK [A-Za-z0-9]" api/ web/app web/lib web/components | grep -v "_test\.go"
    ```
    시험 파일을 빼는 이유: `api/internal/kakao/client_test.go`가 인증 헤더가 올바른지 확인하려면
    `"KakaoAK test-key"`라는 문자열을 갖고 있어야 한다. `test-key`는 누가 봐도 가짜이고,
    이 검사가 찾는 것은 실수로 커밋된 진짜 열쇠다.

## 13. 시작 전에 필요한 준비물

**카카오 REST API 키 하나.** https://developers.kakao.com 에서 애플리케이션을 만들면 발급된다. 발급 후 서버를 켜는 환경에 아래처럼 넣는다.

```
KAKAO_REST_API_KEY=<발급받은 키>
```

이 키는 소스 코드에 절대 넣지 않는다. `api/.env` 파일에 두고 `.gitignore` 에 등록한다.

**열쇠가 없어도 개발과 시험은 전부 진행된다.** 시험은 가짜 응답으로 돌아가고, 서버도 열쇠 없이 켜져서 `not_configured` 오류를 정상적으로 돌려준다. 열쇠는 실제 데이터를 눈으로 확인하는 마지막 단계(10절 5번)에서만 필요하다.
