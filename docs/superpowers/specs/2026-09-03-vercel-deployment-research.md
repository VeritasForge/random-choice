# 점심 결정 서비스를 Vercel에 올리는 방법 — 조사 결과

조사 시점: 2026년 9월 3일
대상: 한 저장소 안에 Next.js 화면(`web/`)과 Go 서버(`api/`)가 나뉘어 있는 이 프로젝트

---

## 한 문단 요약

**이 저장소는 이미 Vercel이 권하는 구조를 갖추고 있습니다.** 화면과 서버를 각각 배포하고,
브라우저는 화면 주소로만 요청하며, 화면이 그 요청을 서버로 중계하는 방식입니다. Vercel
공식 커뮤니티 운영진이 2025년 8월에 권고한 것이 정확히 이 형태였습니다. 따라서 남은 결정은
"구조를 어떻게 바꿀까"가 아니라 **"Go 서버를 어디서 돌릴까"** 하나로 좁혀집니다. 권하는
순서는 **가장 간단한 것부터**입니다. 도커 파일 없이 Go를 그대로 올려 보고, Go 1.26 빌드가
실패하거나 기록이 안 보이면 그때 컨테이너로 옮기고, 서버가 잠들었다 깨는 시간이 참기 어려울
만큼 길면 그때 Vercel 밖(월 2달러 남짓)을 고려하는 것입니다. Vercel 안에서 돌리는 두 방법은
2026년에 나온 새 기능이라 문서는 갖춰졌지만 **실제로 써 봤다는 기록이 인터넷 어디에도
없습니다.** 개인 프로젝트이고 무료 요금제는 한도를 넘겨도 청구서가 아니라 정지로 끝나므로,
새 길을 시험해 볼 여유가 있는 처지입니다.

**한 프로젝트로 합치는 방식(Services)은 권하지 않습니다.** 이유는 아래 2-2절에 적었습니다.

---

## 1. 지금 구조가 이미 맞습니다

### 무엇이 이미 되어 있나

브라우저는 화면 주소의 `/api/v1/nearby`만 부릅니다. 화면(Next.js)이 그 요청을 받아 Go
서버로 넘깁니다. 이 중계 설정은 `web/next.config.ts`에 이미 들어 있습니다.

```
브라우저 ──▶ 화면(Next.js) ──중계──▶ Go 서버 ──▶ 카카오 API
         같은 주소라              환경변수
         교차 출처 문제 없음        API_ORIGIN으로 지정
```

### 왜 이것이 맞는 구조인가

Vercel 공식 커뮤니티에서 같은 상황(nginx로 `/api`를 백엔드에 넘기던 구조를 Vercel로 옮기려는
경우)을 물은 사람에게 운영진이 답한 내용입니다.

> "Easiest to run the frontend and backend as their own projects since you've already got
> them split like that."
> (이미 그렇게 나눠 두셨으니, 화면과 서버를 각각의 프로젝트로 돌리는 것이 가장 쉽습니다.)

단일 도메인을 유지하고 싶다는 재질문에는 "외부 서비스로 향하는 프록시 rewrites를 쓰라"고
안내했습니다. **지금 `next.config.ts`가 하는 일이 바로 그것입니다.**

### 이 구조가 이미 해결해 둔 것

| 항목 | 상태 |
|---|---|
| 교차 출처 요청 문제 | 브라우저가 화면 주소만 부르므로 애초에 발생하지 않습니다 |
| 카카오의 저장 금지 정책 | 서버가 모든 응답에 저장 금지 표시를 붙이고, 시험으로 지키고 있습니다 |
| 각각 따로 배포하고 되돌리기 | 프로젝트가 나뉘어 있어 한쪽만 되돌릴 수 있습니다 |

## 2. 결정할 것은 하나입니다 — Go 서버를 어디서 돌릴까

### 선택지 셋

| 방법 | 실제로 써 본 사례 | 이 프로젝트와의 궁합 |
|---|---|---|
| **가. Vercel에 도커 컨테이너로** | **없음** (2026년 신기능) | 좋음 — 아래 설명 |
| **나. Vercel의 Go 전용 방식으로** | **없음** (2026년 신기능) | 나쁨 — 가보다 나을 이유가 없음 |
| **다. Vercel 밖에** (Fly.io 등) | 있음 (실제 이전 사례) | 무난 — 대신 잃는 것이 있음 |

### 가. 도커 컨테이너로 올리기

**이 프로젝트에 맞는 이유가 셋 있습니다.** 어느 하나가 결정적인 것은 아니고, 셋이 같은
방향을 가리킵니다.

1. **Go 버전을 직접 고릅니다.** Vercel이 Go 1.26을 지원하는지 문서에 나와 있지 않은데,
   컨테이너는 기반 이미지를 내가 정하므로 이 물음 자체가 사라집니다. 셋 중 가장 확실한
   이득입니다.
2. **기다리는 시간에는 요금이 붙지 않습니다.** 이 서버는 요청 시간의 대부분을 카카오 응답을
   기다리는 데 씁니다. Vercel은 코드가 실제로 도는 동안만 처리 요금을 매기고, 기다리는
   동안에는 매기지 않는다고 컨테이너 문서에 명시되어 있습니다.
3. **서버 기록이 수집되고, 서버를 안전하게 끄는 코드도 동작합니다.** 컨테이너의 표준 출력이
   Vercel 기록 화면에 들어옵니다. 종료 신호도 30초 유예와 함께 전달되는데, 이 서버는 그
   신호를 받아 최대 25초를 기다리도록 짜여 있어 그 안에 들어갑니다.

**단, 세 번째 이유는 처음 판단보다 작습니다 — 스스로 정정합니다**

조사 과정에서 저는 "종료 신호 지원 여부가 승부를 갈랐다"고 썼는데, **과장이었습니다.**
검증 과정에서 이 저장소의 화면 코드를 다시 열어 확인한 결과, 서버가 갑자기 끊겼을 때
브라우저는 이미 오류를 잡아 안내 문구와 **"다시 시도" 버튼**을 그립니다. 즉 종료 신호를
못 받았을 때의 실제 손해는 **"드물게 재배포와 겹친 사용자가 버튼을 한 번 더 누르는 것"**
입니다. 게다가 서버가 내려가는 것은 5분간 트래픽이 없을 때이므로, 손해가 발생하려면
"쓰는 사람이 있는데 마침 그때 재배포가 겹치는" 드문 교차가 필요합니다.

저장하는 데이터가 없는 중계 서버라 데이터가 깨질 위험도 없습니다. 이 항목만으로 도커 파일
관리 부담을 감수할 이유는 되지 못합니다.

**대가**

- 도커 파일을 새로 만들어 관리해야 합니다(기반 이미지 보안 갱신 포함).
- 트래픽이 없으면 5분 뒤(미리보기는 30초 뒤) 서버가 내려갑니다. 점심 무렵에만 쓰이는
  서비스라 **첫 사용자가 서버 기동을 기다릴 가능성이 높습니다.** 다만 그 기동이 실제로 몇
  초인지는 아무도 보고한 적이 없어 **직접 재 봐야 합니다.**

### 나. Go 전용 방식 — 먼저 시도해 볼 값어치는 있습니다

Vercel에는 Go 서버를 그대로 올리는 방식이 따로 있고, 이 저장소의 파일 배치가 그 조건에
정확히 맞습니다(`cmd/server/main.go` 진입점, 포트를 환경변수로 읽는 것). **도커 파일이
필요 없어 가장 간단합니다.**

처음에 저는 이 방식을 "권하지 않는다"고 썼지만, 그 근거로 든 종료 신호 문제가 위에서 본
것처럼 작다면 **판단을 그렇게 세게 쓸 근거가 없습니다.** 정직하게 다시 쓰면 이렇습니다.

- **간단함이 이깁니다**: 파일을 하나도 새로 만들지 않고, 대시보드에서 방식만 고르면 됩니다.
- **다만 확인되지 않은 것이 둘 남습니다**: Go 1.26을 지원하는지 문서에 없고, 실행 특성
  (요금 계산 방식, 기록 수집)도 문서에 명시가 없습니다.
- → **먼저 이 방식으로 배포해 보고, Go 1.26 빌드가 실패하거나 기록이 안 보이면 그때
  컨테이너로 옮기는 순서**가 합리적입니다. 옮기는 비용은 도커 파일 하나를 추가하는
  것뿐이고, 나머지 설정은 그대로 쓸 수 있습니다.

### 다. Vercel 밖에 두기

실제로 이 길을 택한 사례가 있습니다. 모니터링 서비스를 만드는 소규모 팀이 백엔드를
Vercel에서 Fly.io로 옮긴 기록입니다.

> "We are a bootstrap business and it difficult for us to predict our monthly expenses."
> (저희는 자체 자금으로 운영하는 사업이라 월 지출을 예측하기 어렵습니다.)
> "However, if you require a hosting an application other than Next.js, it may not be the
> best option."
> (다만 Next.js가 아닌 애플리케이션을 올려야 한다면 최선의 선택이 아닐 수 있습니다.)

비용은 월 150달러 예상에서 23달러대로 줄었습니다. 다만 같은 글에서 **"Fly 쪽 배포가
Vercel보다 시간 초과가 잦아 신뢰성은 떨어졌다"**고 스스로 인정했습니다. 일방적인 승리담이
아닙니다.

가장 작은 인스턴스를 계속 켜 두면 월 2달러 남짓이고, 서버가 내려가지 않으니 기동 대기가
없습니다. **대신 잃는 것**은 미리보기 배포끼리 짝이 맞는 편의, 한곳에서 보는 기록과 지표,
그리고 배포 절차가 하나로 끝나는 단순함입니다.

## 2-2. 한 프로젝트로 합치는 방식을 권하지 않는 이유

Vercel에는 2026년 6월부터 여러 언어의 앱을 **한 프로젝트에 담는 기능**이 있습니다. 공식
문서가 이 상황을 위해 만들었다고 밝힌 기능이고, Go 서버 문서 스스로 "화면과 같은 프로젝트에
Go 서버를 함께 두려면 이 기능을 쓰라"고 지목합니다. 그래서 진지하게 검토했지만, 결론은
권하지 않는 쪽입니다.

### 이 기능이 실제로 주는 이점 — 하나는 진짜입니다

**미리보기 배포의 짝이 커밋 단위로 정확히 맞습니다.** 한 커밋에 화면과 서버를 같이 고쳐
올리면 둘이 하나의 배포로 묶이므로, 미리보기를 열었을 때 반드시 같은 커밋의 조합을 봅니다.

프로젝트를 나눠 두면 이 보장이 한 단계 약해집니다. 나눈 상태에서도 미리보기끼리 묶는 설정이
있지만, 그것이 가리키는 것은 **"그 가지(브랜치)의 최신 배포"**입니다. 그래서 이런 일이
생길 수 있습니다.

> 화면과 서버를 함께 고친 커밋을 올립니다. 서버 쪽 빌드가 먼저 끝나고 화면 빌드가 아직
> 도는 동안, 이미 올라가 있던 **이전 화면**이 **새 서버**를 가리킵니다. 주고받는 형식이
> 바뀐 변경이라면 그 사이에 미리보기를 열어 본 사람은 어긋난 조합을 보게 됩니다.

### 그럼에도 권하지 않는 이유 셋

1. **화면과 서버가 항상 함께 되돌아갑니다.** 공식 문서의 표현으로 "하나만 따로 내보내거나
   되돌릴 수 없습니다." 화면의 사소한 실수 하나로 서버까지 같이 되돌아갑니다. 이것은 요금제
   등급과 무관한 구조적 성질이라 개인 프로젝트에도 그대로 적용됩니다. **이것이 가장 큰
   이유입니다.**
2. **써 봤다는 기록이 인터넷에 하나도 없습니다.** 검색이 전부 Vercel 자사 문서와 데모로
   수렴했고, 그 데모 저장소는 별이 2개입니다.
3. **지금 잘 돌아가는 구조를 바꿔야 합니다.** 화면의 중계 설정을 걷어내고, 대시보드에서
   프로젝트 방식을 바꾸고, 서비스 안에서는 미들웨어를 못 쓴다는 제약을 새로 떠안습니다.

### 베타라는 점은 어떻게 볼 것인가 — 과장하지 않겠습니다

Vercel 문서에 "베타 제품을 온전한 운영 환경에서 쓰는 것을 권하지 않는다"는 문장이 있고,
이것은 사실입니다. 다만 같은 자리의 앞 문장인 "서비스 수준 협약이 적용되지 않는다"는 부분은
**기업 요금제에 한정된 이야기**라, 애초에 그런 협약이 없는 개인 프로젝트에는 해당 사항이
없습니다. 그러므로 "베타라서 안 된다"를 이 판단의 주된 근거로 삼지는 않았습니다. 위의 세
이유, 특히 첫 번째가 근거입니다.

## 3. 새 기능을 쓰는 것이 왜 위험한가 — 그리고 왜 감수할 만한가

### 실사용 기록이 전혀 없습니다

조사에서 가장 뚜렷한 발견입니다. Vercel이 2026년에 내놓은 세 기능 모두 **써 봤다는 글을
찾지 못했습니다.**

| 기능 | 검색 결과 |
|---|---|
| 여러 앱을 한 프로젝트에 담는 기능 | 공식 블로그·문서·자사 데모만 나옴. 그 데모 저장소는 별 2개 |
| 도커 컨테이너 배포의 기동 지연 체감 | 직접 써 본 후기 없음 |
| 프로젝트끼리 미리보기를 묶는 설정 | 경험담 없음 |

기능이 나온 지 두 달 남짓이라 사례가 쌓일 시간이 없었던 것으로 보입니다.

### 그럼에도 시험해 볼 만한 이유

- 개인 프로젝트입니다. 실패해도 되돌리면 그만이고, 회사 서비스가 멈추는 것과는 무게가
  다릅니다.
- 무료 요금제는 한도를 넘기면 **요금이 청구되는 것이 아니라 정지**됩니다. 트래픽 급증으로
  거액이 청구된 사고(한 앱이 한 주에 9만 6천 달러를 청구받은 일)가 구조적으로 일어나지
  않습니다.
- 아무도 재 보지 않은 값(기동 시간 등)을 직접 확인하게 되는데, 그 자체가 얻는 것입니다.

### 다만 오래된 평판을 그대로 믿으면 안 됩니다

"Vercel은 기동 지연이 심하다"는 말이 널리 퍼져 있고 실제 불만 기록도 있습니다.

> "API endpoints are basically useless on Vercel because of the cold start issue."
> (기동 지연 문제 때문에 Vercel에서 API 엔드포인트는 사실상 쓸모가 없습니다.)

하지만 이 발언들은 **2021~2023년의 구형 방식**에 대한 것입니다. 그 뒤로 실행 방식이 두 번
바뀌었습니다(2025년 초, 2026년). **지금도 같다고 단정할 근거가 없고, 나아졌다고 단정할
근거도 없습니다.** 직접 재는 수밖에 없습니다.

## 4. 어느 쪽을 택하든 해야 할 일

### 반드시 해야 하는 것

| 할 일 | 안 하면 무슨 일이 나는가 |
|---|---|
| **실행 지역을 서울로 바꾸기** | 기본값이 미국 워싱턴입니다. 이 서버는 요청마다 카카오를 실시간으로 부르므로(저장이 금지되어 미리 담아 둘 수 없습니다) 태평양을 왕복하는 시간이 사용자 대기에 그대로 더해집니다 |
| **포트 값 맞추기** | Vercel은 기본적으로 80번 포트로 요청을 보내는데 이 서버는 8080에서 듣습니다. 값을 맞추지 않으면 **요청이 아예 닿지 않습니다** |
| **`.gitignore`에 `.vercel` 추가** | 지금 빠져 있습니다. Vercel과 저장소를 연결하면 생기는 폴더가 그대로 커밋됩니다 |
| **미리보기용 카카오 열쇠를 나눌지 정하기** | 미리보기 배포는 별도 자원을 받지 않습니다. 그대로 두면 **미리보기에서 시험할 때마다 실서비스의 카카오 호출 한도를 깎습니다** |

### 하면 좋은 것

- **요청 빈도 제한**을 Vercel 방화벽으로 겁니다. 무료 요금제에서도 프로젝트당 규칙 하나를
  쓸 수 있고, **코드를 고칠 필요가 없습니다.** 남은 과제로 적어 두었던 항목이 이것으로
  해결됩니다. 처음에는 "기록만" 으로 걸어 두고 실제 트래픽을 본 뒤 차단으로 바꾸는 것이
  문서가 권하는 순서입니다.
- 응답에 배포 정보(환경·브랜치·커밋)를 실어 두면 "이 응답이 이 미리보기에서 나온 것"을
  추측이 아니라 확인으로 바꿀 수 있습니다. Vercel 공식 예제가 쓰는 방법입니다.

## 4-2. 올린 뒤에 어떻게 관리하나 — 기록과 지표

배포만큼 중요한 것이 "문제가 났을 때 무엇을 볼 수 있는가"입니다. 조사에서 확인한 것을
정리합니다.

### ⚠️ 무료 요금제의 가장 큰 제약은 기록 보관 기간입니다

| 요금제 | 실행 기록 보관 |
|---|---|
| **무료** | **한 시간** |
| 유료(Pro) | 하루 |
| 유료 + 관측 부가 기능 | 30일 |

**어떤 배포 방식을 택하든 무료 요금제에서는 한 시간 지난 문제를 기록으로 추적할 수
없습니다.** "기록이 불편할까"라는 물음의 가장 실질적인 답은 배포 방식이 아니라 요금제입니다.
점심시간에 생긴 문제를 저녁에 들여다보려 하면 이미 기록이 사라진 뒤입니다.

### 방식마다 볼 수 있는 것이 다릅니다

| 방식 | 전용 관측 화면 | Go 서버의 출력 |
|---|---|---|
| **지금 구조(별도 프로젝트 + 중계)** | 있음 — 외부 중계 전용 화면에서 요청 수와 대상별 분류를 봅니다 | 컨테이너로 올리면 표준 출력이 실행 기록에 수집됩니다 |
| 한 프로젝트로 합치기 | **없음** — 관측 화면 목록에 해당 항목이 없습니다 | 서비스별로 기록을 거를 수 있다는 설명이 발표 글에는 있으나, 참조 문서 여섯 곳에는 그런 항목이 없습니다 |

지금 구조를 유지하면 관측 수단이 **문서로 더 분명하게 확인됩니다.** 합치는 쪽은 기능이
있다는 근거가 발표 글과 안내 글에만 있고 참조 문서에 반영되어 있지 않습니다. 기능이 없다는
뜻은 아니고, **아직 문서가 따라오지 못한 상태**로 읽는 것이 정확합니다.

### 컨테이너의 기록에는 한 가지 약점이 있습니다

컨테이너의 표준 출력은 실행 기록에 들어오지만, **어느 요청에서 나온 기록인지 묶이지
않습니다.** Vercel 문서의 표현으로는 그 순간 처리 중인 모든 요청에 함께 표시됩니다. 이
서버는 구조화된 기록을 쓰고 있어 완화되지만, 동시에 여러 요청이 들어오면 구분이 흐려집니다.

### 배포 이력 관리

프로젝트를 나눠 두면 화면과 서버를 각각 되돌릴 수 있습니다. 한 프로젝트로 합치면 **항상
함께** 되돌아갑니다. 다만 이것은 양날인데, 화면과 서버를 한 커밋에서 같이 고친 경우에는
함께 되돌아가는 쪽이 오히려 안전합니다. 규격이 어긋난 조합이 남지 않기 때문입니다.

## 5. 첫 배포에서 반드시 재 볼 것

문서로는 답이 나오지 않아 **실제로 해 봐야만 알 수 있는 것들**입니다. 이 목록이 이번 조사의
정직한 한계이기도 합니다.

1. **서버가 처음 깨어나는 데 몇 초 걸리는가** — 사용자 체감을 좌우하는데 아무도 보고한 적이
   없습니다. 이 값이 작으면 Vercel 안에 두는 선택이 훨씬 유리해집니다.
2. **포트 설정이 제대로 먹었는가** — 안 먹으면 요청이 하나도 닿지 않습니다.
3. **카카오 호출이 인증서 검증을 통과하는가** — 가벼운 기반 이미지에는 루트 인증서가 없어
   HTTPS 호출이 실패할 수 있습니다. Vercel 공식 예제의 도커 파일에는 이 설정이 없는데, 그
   예제의 Go 서버는 바깥을 부르지 않기 때문입니다. **이 프로젝트는 카카오를 부르므로 필요할
   것으로 보이나 확인이 필요합니다.**
4. **Go 로그가 Vercel 기록 화면에 보이는가**
5. **한쪽만 고친 커밋이 양쪽을 다 빌드하는가** — 이 저장소는 자바스크립트 작업공간 규칙을
   쓰지 않아 Vercel의 자동 건너뛰기 조건에 맞지 않습니다. 낭비가 실제로 생기는지 봐야 합니다.
6. **Go 1.26 빌드가 성공하는가**
7. **미리보기끼리 짝을 맞추는 설정이 빌드 시점에 동작하는가** — 화면의 중계 주소는 빌드할 때
   굳는데, 그 값이 빌드 시점에 주어지는지 문서에 명시가 없습니다.
   **⚠️ 이 항목은 실패해도 조용합니다.** 값을 못 찾으면 설정이 대체값(로컬 주소)으로
   조용히 넘어가고, 배포본의 모든 조회 요청이 실패하는데 화면에는 아무 단서가 남지
   않습니다. 지금 코드는 그럴 때 빌드 기록에 경고 한 줄을 남기도록 되어 있으니,
   **첫 배포의 빌드 기록에서 그 경고가 뜨지 않았는지 반드시 눈으로 확인해야 합니다.**

## 7. 사용자가 정해야 할 것

조사자가 대신 정하지 않고 남겨 둡니다.

1. **Go 서버를 Vercel 안에 둘 것인가, 밖에 둘 것인가.** 안에 두면 통합의 편의를 얻고 검증
   안 된 새 기능에 기댑니다. 밖에 두면 검증된 길을 가는 대신 월 2달러 남짓과 통합의 편의를
   맞바꿉니다.
2. **Go를 계속 쓸 것인가.** 서버 쪽 코드는 구현 816줄에 시험 1,433줄로, 시험이 구현의
   1.75배인 잘 검증된 코드입니다. 화면과 같은 언어로 다시 쓰면 배포 구성 문제가 통째로
   사라지지만 그 2,249줄을 버려야 합니다. **Go를 고른 이유(학습 목적인지, 취향인지, 다른
   곳에 쓸 계획인지)를 모르는 상태에서 조사자가 권할 일이 아닙니다.**

## 갈래 A: 별도 프로젝트 두 개 + Go는 컨테이너 (조사상 최적 후보)

### A-1. `api/Dockerfile.vercel` (새 파일)

공식 예제(`vercel-labs/full-stack-service-previews`)의 구조를 이 저장소에 맞춘 것이다.

```dockerfile
FROM golang:1.26-alpine AS build

WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download

COPY . .
# -trimpath와 -ldflags는 공식 예제와 같다. 디버그 정보를 빼서 바이너리를 줄인다.
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /server ./cmd/server

FROM alpine:3.22

# 카카오 API를 HTTPS로 부르므로 루트 인증서가 필요하다.
# 공식 예제에는 이 줄이 없지만, 그 예제의 Go 서비스는 바깥으로 나가지 않는다.
RUN apk add --no-cache ca-certificates

RUN addgroup -S app && adduser -S -G app -u 10001 app
COPY --from=build /server /server

# Vercel의 컨테이너 라우터가 읽는 포트와 서버가 듣는 포트를 맞춘다.
# 비루트 사용자는 1024 미만 포트를 열 수 없으므로 80을 쓸 수 없다.
ENV PORT=8080

USER app
CMD ["/server"]
```

**주의 1**: `ca-certificates`를 넣지 않으면 카카오 HTTPS 호출이 인증서 검증에 실패한다.
- **정확한 이유**: 알파인 최소 이미지에 **루트 인증서 묶음 파일 자체가 없기** 때문이다.
  Go의 `crypto/x509`는 `CGO_ENABLED` 설정과 **무관하게** 파일시스템의 인증서 묶음을 읽는다.
  ("CGO를 껐기 때문"이라고 적으면 다음 사람이 "CGO를 켜면 안 넣어도 되나"로 잘못 이해한다)
- 공식 예제에 이 줄이 없는 이유는 그 예제의 Go 서비스가 바깥 API를 부르지 않기 때문이다.
  **이 저장소는 카카오를 부르므로 필요하다** — 첫 배포에서 실제로 확인할 항목이다.

**주의 2**: `ENV PORT=8080`만으로 충분한지, Vercel 프로젝트 설정에도 `PORT`를 넣어야 하는지
문서가 명확하지 않다. 공식 안내는 프로젝트 설정에 넣으라고 한다:
`vercel env add PORT production --no-sensitive`

### A-4. `web/next.config.ts` 수정

```ts
import type { NextConfig } from "next";
import { withRelatedProject } from "@vercel/related-projects";

// 브라우저는 자기 주소의 /api로만 요청하고, Next.js가 그 요청을 Go 서버로 넘긴다.
// 이렇게 하면 브라우저 입장에서 같은 출처라 교차 출처 허용 설정이 필요 없다.
//
// 주소를 고르는 순서는 세 단계다.
//   1. 미리보기·운영 배포에서는 짝이 되는 Go 프로젝트 주소를 Vercel이 알려준다.
//   2. 그 값이 없으면 API_ORIGIN 환경변수를 쓴다(로컬 개발과 명령줄 배포).
//   3. 그것도 없으면 로컬 기본값을 쓴다.
// 2단계가 필요한 이유는 relatedProjects가 명령줄 배포에서는 동작하지 않기 때문이다.
const apiOrigin = withRelatedProject({
  projectName: "random-choice-api", // Vercel 프로젝트 이름과 정확히 같아야 한다
  // 기본값은 8080이다. Go 서버도 PORT가 없으면 8080에서 듣기 때문이다
  // (api/cmd/server/main.go). Justfile의 `just dev`가 8090을 쓰는 것은
  // 그 명령이 양쪽에 8090을 함께 넘겨 주기 때문이지, 기본값이 8090이어서가 아니다.
  // 여기에 8090을 적으면 README대로 손으로 띄운 로컬 개발이 깨진다.
  defaultHost: process.env.API_ORIGIN ?? "http://localhost:8080",
});

// 이 값은 빌드할 때 굳는다. 배포 빌드에서 어느 쪽도 잡히지 않으면 배포본의 모든
// /api 요청이 개발용 주소로 나가 전부 실패하는데, 화면에는 아무 단서도 남지 않는다.
if (
  !process.env.VERCEL_RELATED_PROJECTS &&
  !process.env.API_ORIGIN &&
  process.env.NODE_ENV === "production"
) {
  console.warn(
    "[random-choice] Go 서버 주소를 찾지 못해 http://localhost:8090 으로 빌드합니다. " +
      "배포본에서는 브라우저의 /api 요청이 전부 실패합니다.",
  );
}

const nextConfig: NextConfig = {
  async rewrites() {
    return [{ source: "/api/:path*", destination: `${apiOrigin}/api/:path*` }];
  },
};

export default nextConfig;
```

**확인 필요**: `withRelatedProject`는 소스상 `https://호스트` 형태의 전체 주소를 돌려준다
(소스 직접 확인함). 따라서 `${apiOrigin}/api/:path*`가 올바른 주소가 된다.
다만 `VERCEL_RELATED_PROJECTS`가 **빌드 시점에** 주입되는지는 문서로 확인하지 못했다.
Turborepo 관련 주의 문구가 간접 근거이나 단정할 수 없다 — **첫 배포에서 반드시 확인할 것**.

### A-7. 대시보드에서 할 일
1. 프로젝트 두 개를 만들고 각각 Root Directory를 `web/`, `api/`로 지정
2. Go 프로젝트: 환경변수 `KAKAO_REST_API_KEY`, `PORT=8080` 설정
3. web 프로젝트: 방화벽에 요청 빈도 제한 규칙 1개 추가 (조건에 경로 `/api/*`, 동작은
   처음엔 "기록만"으로 두고 관찰한 뒤 차단으로 바꾼다)
4. 두 프로젝트 모두 리전을 서울(icn1)로
5. 미리보기 환경의 카카오 키를 운영과 분리할지 결정 (미리보기는 인프라를 복제해 주지
   않으므로, 그대로 두면 미리보기 시험이 운영 할당량을 깎는다)

## 갈래 B: Services 한 프로젝트

### `vercel.json` (저장소 루트)

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["icn1"],
  "services": {
    "web": {
      "root": "web/",
      "framework": "nextjs"
    },
    "api": {
      "root": "api/",
      "framework": "go"
    }
  },
  "rewrites": [
    { "source": "/api/(.*)", "destination": { "service": "api" } },
    { "source": "/(.*)", "destination": { "service": "web" } }
  ]
}
```

- 규칙 순서가 중요하다. 구체적인 것을 먼저, 모두 잡는 `/(.*)`를 마지막에 둔다
- 서비스는 **원본 경로를 그대로** 받는다. Go가 이미 `/api/v1/...`로 마운트되어 있어
  경로 변환이 필요 없다 — 이 저장소에 유리한 점이다
- 대시보드에서 프로젝트 프레임워크를 **Services**로 바꿔야 한다.
  `vercel.json`에 `services` 키가 있는 것만으로는 켜지지 않는다
- 이 구성에서는 `web/next.config.ts`의 `rewrites`를 **제거해야 한다.**
  최상위 라우팅이 이미 `/api/*`를 Go로 보내므로 중복이다

### Go를 컨테이너로 바꾸려면
`"api"`의 `framework: "go"`를 지우고 `"entrypoint": "Dockerfile.vercel"`로 바꾼다.
정상 종료(SIGTERM 30초)와 Go 1.26 통제를 얻는다.

## 두 갈래 공통으로 확인해야 할 것 (첫 배포에서)

1. 컨테이너 첫 기동이 실제로 몇 초 걸리는가 (사용자 체감을 좌우한다)
2. `PORT` 설정이 제대로 먹었는가 (안 먹으면 요청이 아예 닿지 않는다)
3. 카카오 HTTPS 호출이 인증서 검증에 성공하는가 (`ca-certificates` 필요 여부)
4. Go의 로그가 런타임 로그에 나타나는가
5. 한쪽만 고친 커밋이 양쪽을 다 빌드하는가
6. Go 1.26 빌드가 성공하는가
