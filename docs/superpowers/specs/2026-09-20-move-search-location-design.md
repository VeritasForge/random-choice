# 위치를 옮겨 찾기 — 설계 문서

## 1. 한 문단 요약

지금 이 서비스는 브라우저가 알려 주는 현재 위치에서만 음식점을 찾습니다. 좌표를
만드는 곳이 `web/lib/geo.ts`의 위치 확인 하나뿐이기 때문입니다. 그래서 여행을
계획하거나 다른 동네에 갈 일이 있는 사람은 쓸 방법이 없고, 위치 권한을 거부한
사람은 "자물쇠 아이콘을 눌러 허용하세요"라는 안내 앞에서 더 나아가지 못합니다.
이번 변경은 시작 화면에 `다른 곳에서 찾기`를 더해서, 사용자가 `경주`처럼 장소
이름을 적어 그 자리를 고르면 그 좌표로 지금과 똑같은 조회가 돌게 만듭니다.
카카오의 장소 이름 검색(`/v2/local/search/keyword.json`) 하나만 새로 붙이고,
좌표를 손에 넣은 뒤의 흐름은 기존 코드를 그대로 씁니다. 브라우저에는 사용자가
직접 친 글자 하나만 남기고 카카오가 돌려준 장소 이름과 좌표는 남기지 않습니다.

## 2. 왜 이 기능이 필요한가

**첫째, 여행이나 외출을 앞둔 사람이 쓸 수 없습니다.** 이 서비스의 가치는 "뭘
먹을지 먼저 좁혀 준다"는 것인데, 그 도움이 가장 필요한 때가 낯선 동네에 있을
때입니다. 자기 동네에서는 아는 가게가 이미 몇 곳 있지만 처음 간 곳에서는 후보
자체를 떠올리지 못하기 때문입니다. 지금은 그 자리에 실제로 서 있어야만 쓸 수
있습니다.

**둘째, 위치 권한을 거부한 사람에게 막다른 길이 남아 있습니다.** `web/lib/errors.ts`의
`permission_denied` 안내는 브라우저 설정을 고치라고 말하는데, 고치고 싶지 않은
사람에게는 이 서비스를 쓸 방법이 아예 없습니다. 장소를 적어서 찾는 길이 생기면
위치 권한 없이도 서비스 전체가 돌아갑니다.

`README.md`의 "아직 없는 것들" 목록에 **"주소를 직접 입력해 위치 지정"**이 이미
적혀 있습니다. 이번 변경은 그 자리를 채우는 일입니다.

## 3. 실측으로 확인한 것 — 카카오 장소 이름 검색의 성질

아래 수치는 모두 2026-09-20에 이 저장소의 카카오 열쇠로 직접 조회해 얻은
값입니다. 카카오 응답은 바뀔 수 있으므로 시간이 지난 뒤에는 다시 재야 합니다.

### 3-1. 주소 검색은 혼자 쓸 수 없고, 쓸 수 있을 때도 자리가 엉뚱합니다

카카오에는 성격이 다른 두 경로가 있습니다. 장소 이름 검색(`keyword.json`)과 주소
검색(`address.json`)입니다. 일곱 개 검색어로 둘을 나란히 불러 봤습니다.

| 검색어 | 장소 이름 검색 상위 결과 | 주소 검색 결과 |
|---|---|---|
| `강남역` | 강남역 2호선(지하철역), 강남역 신분당선, 놀숲 강남역점(카페) | **0건** |
| `홍대입구` | 홍대입구역 2호선, 홍대입구역 공항철도, 홍익대학교 정문 | **0건** |
| `애월` | 곽지해수욕장, 9.81파크 제주, 새별오름(모두 관광명소) | 제주시 애월읍 1건 |
| `해운대` | 해운대해수욕장, 동백섬, 송정해수욕장 | 부산 해운대구 1건 |
| `경주` | 동궁과월지, 경주 황리단길, 첨성대 | 경북 경주시 1건 |

**사람이 실제로 떠올리는 말인 `강남역`과 `홍대입구`에 주소 검색은 아무것도 주지
않습니다.** 역 이름은 주소가 아니기 때문입니다.

**주소 검색이 답을 주는 경우에도 그 좌표는 점심을 찾기에 맞지 않습니다.**
행정구역 하나의 중심점이라서 사람이 실제로 밥을 먹는 자리와 멀리 떨어져
있습니다. 주소 검색이 준 제주시 애월읍 중심 좌표에서 재 보니 곽지해수욕장까지
2,594m, 9.81파크 제주까지 8,734m였습니다. 점심에 걸어갈 수 있는 거리는 기껏해야
몇백 미터이므로 이 중심점은 그 범위 안에 들어가지 못합니다.

**장소 이름 검색은 주소 문자열까지 받아 줍니다.** `제주시 애월읍`을 그대로
넣었더니 곽지해수욕장과 9.81파크가 나왔고, `서울 마포구 동교동`을 넣었더니
홍대땡땡거리가 나왔습니다. 즉 주소를 아는 사람도 장소 이름 검색 하나로
해결됩니다.

**그래서 장소 이름 검색 하나만 붙이고 주소 검색은 만들지 않습니다.**

### 3-2. 한 검색어가 내주는 것은 많아야 45곳이고, 그보다 적을 때도 많습니다

카카오가 "있다고 말하는 수"(`total_count`)와 "실제로 내주는 수"(`pageable_count`)가
다릅니다.

| 검색어 | 있다고 말하는 수 | 실제로 내주는 수 |
|---|---:|---:|
| 경주 | 33,046 | 45 |
| 해운대 | 28,528 | 45 |
| 애월 | 6,000 | 45 |
| 강남역 | 2,575 | **34** |
| 판교역 | 260 | **41** |
| 홍대입구 | 147 | **36** |
| 울릉도 저동항 | 5 | 5 |

한 번에 받을 수 있는 최대는 15곳입니다(16을 요청하면 `should be at most 15`라는
400 오류가 옵니다). 45곳이 상한이지만 강남역은 34곳, 홍대입구는 36곳에서
끝납니다. **그러므로 "3페이지면 끝"을 코드에 적어 두면 안 되고, 카카오가 주는
`is_end` 표시를 읽어서 멈춰야 합니다.**

페이지를 나누는 크기는 우리가 정합니다. 15개씩이면 3페이지, 5개씩이면
9페이지이고 합계는 같습니다. 이 설계는 15개씩 받습니다. 카카오가 허용하는 최대라
호출 횟수가 가장 적기 때문입니다.

### 3-3. 마지막 페이지를 넘겨 요청하면 오류가 아니라 마지막 페이지를 다시 줍니다

15개씩 받을 때 4페이지를 요청하니 3페이지와 똑같은 열다섯 곳(첫 항목이 둘 다
`경주버드파크`)이 왔습니다. 5개씩 받을 때도 10페이지가 9페이지와 같았습니다.
**끝났다는 표시를 보지 않고 계속 넘기면 같은 항목이 목록에 끝없이 쌓입니다.**
이것이 이 기능에서 가장 빠지기 쉬운 함정입니다.

### 3-4. 같은 45곳 상한인데 음식점 조회와 사정이 다릅니다

음식점 조회에서는 이 상한이 진짜 문제였습니다. 반경 500m 안에 900곳이 있는데
45곳만 오고, 사용자가 무엇을 바꿔도 같은 45곳이 왔습니다. 그래서 조회 지점을
아홉 곳으로 늘리는 우회 설계를 했습니다(`2026-09-19-search-coverage-expansion-design.md`).

장소 이름 검색에서는 문제가 되지 않습니다. 실측에서 사람이 찾는 자리가 대개
위쪽에 있었고(`경주`의 황리단길이 두 번째, `애월`의 곽지해수욕장이 두 번째),
못 찾으면 `경주 보문단지`처럼 더 좁혀서 다시 치면 됩니다. **차이는 탈출구의
유무입니다.** 음식점 조회에서는 사용자가 할 수 있는 일이 없어 서버가 지점을
늘려야 했지만, 장소 검색에서는 검색어를 고치는 것으로 사용자가 직접 벗어날 수
있습니다. 그래서 목록 끝에 닿으면 그 탈출구를 안내 문구로 알려 줍니다.

## 4. 무엇을 만드는가

### 4-1. 화면이 이어지는 순서

```
 ① 시작                         ② 위치 검색 (새 화면)
┌──────────────────────┐       ┌────────────────────────────┐
│  오늘은 뭐 먹지?      │       │ ← 돌아가기                 │
│                      │       │ 어디에서 찾을까요?          │
│ [경주로 다시 찾기]    │──┐    │ [ 경주        ] [ 찾기 ]   │
│   ↑ 지난번 글자가     │  │    │ ─────────────────────────  │
│     남았을 때만       │  ├───▶│ 동궁과월지                 │
│ [지금 있는 곳에서]    │  │    │ 경주 황리단길              │
│ [다른 곳에서 찾기]    │──┘    │ 경주월드                   │
│  최근 기록 보기       │       │ …열다섯 곳까지             │
└──────────────────────┘       │ [ 더 보기 ]                │
         │                     └────────────────────────────┘
         │ 지금 있는 곳에서 찾기              │ 하나를 고름
         ▼                                   ▼
      브라우저 위치 확인 ───────────────▶ 좌표 확보
                                             │
                                             ▼
                                   기존 조회가 그대로 돈다
                                   (Go 서버 → 카카오 → 음식 종류·가게 목록)
                                             │
                                             ▼
 ③ 후보 고르기                              ④ 결과
┌──────────────────────┐   종류를 고름     ┌──────────────────────┐
│ 📍 경주 황리단길 주변 │ ────────────────▶ │ 📍 경주 황리단길 주변 │
│           [ 바꾸기 ] │                   │           [ 바꾸기 ] │
│  어느 쪽이 끌리나요?  │                   │      오늘은          │
│ [밥집·백반] [분식]   │                   │    돈까스·우동       │
│ [돈까스·우동][국밥·탕]│                   │ 황남돈까스 120m      │
│ [ 다시 뽑기 ]        │                   │ [ 다른 가게 보기 ]   │
│ [ 정해 주세요 ]      │ ◀──────────────── │ [ ← 후보 다시 보기 ] │
└──────────────────────┘  후보 다시 보기    │ [ 처음부터 다시 ]────┼──▶ ①로
                                           └──────────────────────┘
```

되돌아가는 길은 셋입니다.

- **결과에서 후보로**(`← 후보 다시 보기`): 옮긴 위치 그대로 `다시 뽑기`가
  이어집니다. 지금은 이 길이 없어서 다른 음식 종류를 보려면 처음부터 다시
  해야 하는데, 옮긴 위치에서는 그 비용이 훨씬 큽니다. 검색부터 다시 해야 하기
  때문입니다.
- **후보·결과에서 검색으로**(`바꾸기`): 다른 동네로 옮깁니다.
- **결과에서 시작으로**(`처음부터 다시`): 시작 화면이 뜹니다. 위치를 유지할지
  묻는 별도 화면은 만들지 않습니다. 시작 화면에 `경주로 다시 찾기` 단추가
  이미 있어서 그 화면 자체가 질문이 되기 때문입니다.

### 4-2. 시작 화면 — 단추가 둘, 또는 셋

`web/components/StartScreen.tsx`를 고칩니다.

지난번에 친 글자가 없을 때는 단추가 둘입니다.

```
[ 지금 있는 곳에서 찾기 ]   ← 지금의 "위치 허용하고 시작하기"가 이 이름으로 바뀐다
[ 다른 곳에서 찾기 ]
  최근 기록 보기
```

지난번에 친 글자가 있으면 맨 위에 하나가 더 붙습니다.

```
[ 경주로 다시 찾기 ]        ← 글자가 남아 있을 때만
[ 지금 있는 곳에서 찾기 ]
[ 다른 곳에서 찾기 ]
  최근 기록 보기
```

`경주로 다시 찾기`를 누르면 곧바로 조회되지 않고 **②번 검색 화면으로 가되
입력창에 `경주`가 채워지고 결과 목록이 이미 떠 있는 상태**가 됩니다. 브라우저에
좌표를 남기지 않기로 했으므로 어느 자리였는지를 알 수 없고, 사용자가 목록에서
한 번 더 골라야 하기 때문입니다.

기억하는 글자는 **가장 마지막 것 하나뿐**입니다. 다른 곳을 새로 찾으면 그것으로
바뀝니다. 여러 개를 쌓으면 시작 화면이 복잡해지고 지우는 길도 따로 만들어야
하는데, 그 자리를 기록 화면에 두면 다녀온 가게를 다루는 화면에 성격이 다른 것이
섞입니다.

지금 쓰고 있는 접근성 규칙을 그대로 지킵니다. 조회 중에는 `disabled`가 아니라
`aria-disabled`로 막습니다. 방금 누른 단추를 `disabled`로 만들면 브라우저가 그
단추의 포커스를 떨어뜨려서, 키보드나 화면 낭독기를 쓰는 사람이 자기 위치를
잃기 때문입니다.

### 4-3. 위치 검색 화면 (새 화면)

`web/components/SearchScreen.tsx`를 새로 만듭니다.

- 입력창 하나와 `찾기` 단추 하나를 둡니다. 입력이 비어 있으면 `aria-disabled`로
  막습니다.
- 결과는 한 줄에 **장소 이름**과 **주소**를 보여주고, 카카오가 분류를 붙인
  곳에는 `관광명소` 같은 꼬리표를 함께 답니다. 분류가 빈 곳도 그대로 보여
  줍니다. 실측에서 `동궁과월지`·`첨성대`·`홍익대학교 정문`처럼 분류가 없는 좋은
  후보가 많았기 때문에, 분류로 걸러내면 오히려 필요한 자리가 사라집니다.
- **거르지 않고 카카오가 준 순서 그대로 보여줍니다.** `놀숲 강남역점`(카페)처럼
  잡음이 섞이지만 상위 다섯 개 중 한두 개 수준이고, 그것을 골라도 조회하는
  자리는 강남역 주변과 거의 같아 결과가 크게 달라지지 않습니다.
- 목록 아래에 `더 보기`를 둡니다. 누르면 다음 열다섯 곳을 이어 붙입니다.
- **카카오가 `is_end`로 끝을 알리면 `더 보기`를 감추고** 이렇게 안내합니다:
  "여기까지가 전부입니다. 못 찾으셨다면 `경주 보문단지`처럼 더 좁혀서
  찾아보세요." 3-4절에서 말한 탈출구를 알려 주는 자리입니다.
- 결과가 0건이면 "그런 이름의 장소를 찾지 못했어요. 다른 말로 찾아보세요"를
  보여줍니다.
- `더 보기`로 목록이 늘어난 것은 화면 낭독기에게 소리로 알립니다. 지금
  `StartScreen.tsx`가 쓰는 것과 같은 방식(`role="status"`와 `aria-live="polite"`를
  가진 숨은 영역)을 씁니다. `더 보기`는 화면을 바꾸는 것이 아니므로 포커스는
  그 단추에 그대로 둡니다.

### 4-4. 기준 위치 표시

`web/components/CandidateScreen.tsx`와 `web/components/ResultScreen.tsx` 위쪽에
지금 어디를 기준으로 찾았는지를 한 줄로 표시하고, 그 줄에서 검색 화면으로 가는
`바꾸기`를 둡니다.

- 브라우저 위치로 찾았을 때: `📍 지금 있는 곳`
- 옮긴 위치로 찾았을 때: `📍 경주 황리단길 주변`

옮긴 자리의 이름은 **화면이 켜져 있는 동안에만 들고 있는 값**이고 브라우저에
저장하지 않습니다(4-5절).

### 4-5. 브라우저에 남기는 것 — 사용자가 친 글자 하나

`web/lib/anchor.ts`를 새로 만듭니다. 이름을 `origin`이 아니라 `anchor`로 하는
까닭은, 이 저장소에 이미 `API_ORIGIN`이라는 환경변수가 있어 읽는 사람이 헷갈리기
때문입니다.

```ts
/** 어디를 기준으로 음식점을 찾을 것인가. */
export type Anchor =
  | { kind: "here" }
  | { kind: "spot"; name: string; lat: number; lng: number };
```

저장은 사용자가 친 글자 하나뿐이고, 열쇠는 `random-choice.keyword.v1`입니다.
기존 두 열쇠(`random-choice.visits.v1`, `random-choice.avoid.v1`)와 같은 방식으로
저장소를 밖에서 받는 순수 함수로 만듭니다(`web/lib/visits.ts`와 같은 모양).

**카카오가 준 장소 이름과 좌표는 저장하지 않습니다.** 이 저장소는 카카오가 조회
결과의 저장을 금지한다는 이유로 브라우저에 남기는 것을 엄격히 제한해 왔고, 음식
종류 구분값조차 "카카오 응답을 가공한 값으로 읽힐 여지가 있다"는 이유로 일부러
뺐습니다(`README.md`의 "어떻게 동작하나"). 카카오가 밝힌 저장 허용 예외는
"사용자가 직접 고른 장소의 장소식별값과 상호"까지였고 좌표는 그 문구에 들어
있지 않습니다.

반대로 **사용자가 친 글자는 카카오에서 온 값이 아니라 사용자가 만든 입력**이므로
이 경계와 무관합니다. 이미 저장하고 있는 "최근에 정한 곳 빼기" 스위치와 같은
성격입니다.

### 4-6. 서버에 새로 생기는 경로

**Go 서버** — `api/internal/kakao/client.go`에 장소 이름 검색을 부르는 기능을
더하고, `api/internal/httpapi/handler.go`에 경로를 하나 더합니다.

```
GET /api/v1/places?query=경주&page=1
→ {"places":[{"id","name","address","lat","lng","category"}],"isEnd":false}
```

- 결과 타입은 음식점용 `kakao.Place`와 나눕니다. 장소 검색 결과에는 거리가 없고
  (기준 좌표 없이 부르므로) 음식 분류 문자열도 쓰임이 다르기 때문입니다.
- `page`는 1 이상이어야 하고, 크기는 15로 고정합니다(카카오 상한).
- `query`가 비면 `invalid_query`로 400을 돌려줍니다.
- 카카오 오류 처리(한도 초과·열쇠 거부·그 밖의 실패)는 지금 `/api/v1/nearby`가
  쓰는 것과 같은 갈래를 그대로 씁니다.
- **비밀값 헤더 검사를 이 경로에도 똑같이 겁니다.** 걸지 않으면 조회 한도를
  지키려고 만든 장치에 구멍이 하나 생깁니다.

**화면 서버** — `web/app/api/v1/places/route.ts`를 새로 만듭니다. 지금
`web/app/api/v1/nearby/route.ts`가 그런 것처럼 환경변수를 읽어 넘기기만 하는
껍데기로 두고, 넘기는 규칙은 `web/lib/proxy.ts`에 둡니다. 화면 시험은 브라우저
없이 돌기 때문에 `app/` 아래에 판단을 두면 어떤 시험도 그것을 지키지 못합니다.

**브라우저** — `web/lib/api.ts`에 장소 검색을 부르는 함수를 더합니다. 지금
`fetchNearby`가 그런 것처럼 응답의 모양을 확인한 뒤에 돌려주고, 시간 상한과
오류 코드 처리도 같은 방식을 씁니다. 모양을 확인하지 않고 단정하면 계약이
어긋난 순간이 아니라 한참 뒤 화면이 그 값을 쓰는 자리에서 조용히 망가집니다.

카카오 호출은 검색 한 번에 1회이고 `더 보기`를 끝까지 눌러도 3회입니다. 음식점
조회 한 건이 쓰는 최대 123회에 비하면 미미합니다.

### 4-8. 손대는 파일

★ 표시가 붙은 것이 새로 만드는 파일입니다.

```
web/
├── app/page.tsx                    ← 화면 상태에 "어디를 기준으로 찾았는가"가 더해진다
├── app/api/v1/nearby/route.ts        (그대로)
├── app/api/v1/places/route.ts      ★ 새 파일 — 장소 검색을 Go 서버로 넘기는 껍데기
├── components/
│   ├── StartScreen.tsx             ← 단추가 둘 또는 셋이 된다
│   ├── SearchScreen.tsx            ★ 새 파일 — 위치 검색 화면
│   ├── CandidateScreen.tsx         ← 위에 기준 위치 줄이 붙는다
│   └── ResultScreen.tsx            ← 기준 위치 줄 + `← 후보 다시 보기` 단추
└── lib/

    ├── proxy.ts                    ← 넘기는 규칙을 검색에도 쓴다
    ├── errors.ts                   ← 검색 실패 안내 문구가 는다
    └── anchor.ts                   ★ 새 파일 — 조회 기준점의 타입, 그리고 글자의 저장·조회

api/internal/
├── kakao/client.go                 ← 장소 이름 검색을 부르는 기능이 는다
└── httpapi/handler.go              ← GET /api/v1/places 경로가 는다

README.md                           ← 화면 설명, 시작 단추 이름, 저장하는 것 목록, 한계 목록
```

### 4-7. 빈 결과와 오류

**음식점이 하나도 없을 때**는 지금 있는 빈 결과 화면을 그대로 씁니다. 다만 그
화면의 `다시 찾아보기`는 반경을 2km로 넓혀 다시 찾는데, **지금 코드는 그때
브라우저 위치를 다시 묻습니다**(`web/app/page.tsx`의 `start(WIDER_RADIUS)`).
옮긴 위치에서 이 단추를 누르면 엉뚱하게 사용자가 서 있는 자리로 돌아가므로,
조회 기준점을 함께 넘기도록 고칩니다. **이것이 이번 변경에서 가장 놓치기 쉬운
자리입니다.**

**검색이 실패했을 때**의 안내 문구는 `web/lib/errors.ts`에 더합니다. 그 파일의
시험이 Go 소스에서 오류 코드를 뽑아 표와 대조하므로, 서버에 새로 만드는
`invalid_query`도 자동으로 그 대조에 걸립니다.

## 5. 일부러 만들지 않는 것

- **지도에서 핀을 끌어 위치를 정하는 것.** 브라우저용 열쇠를 새로 발급받고 배포
  도메인을 등록해야 하며 지도 라이브러리가 내려받는 용량에 더해집니다. 이
  서비스는 이미 중심에서 400m와 800m 떨어진 링 여덟 지점까지 훑기 때문에 핀을
  200m 옮기는 정밀도가 결과를 크게 바꾸지 않습니다. 장소 이름 검색을 써 본 뒤에
  "이름으로는 못 짚겠다"는 상황이 실제로 나오면 그때 다시 봅니다.
- **주소 검색(`address.json`).** 3-1절의 이유로 만들지 않습니다.
- **검색 결과를 분류로 걸러내는 것.** 4-3절의 이유로 만들지 않습니다.
- **지난번에 친 글자를 여러 개 쌓아 두는 것.** 4-2절의 이유로 하나만 둡니다.
- **옮긴 위치에서 찾은 기록을 따로 구분하는 것.** `여기로 정했어요` 기록은
  지금처럼 장소식별값과 상호만 남기고, 어디에서 찾았는지는 남기지 않습니다.

## 6. 확인되지 않은 전제 — 사람이 판단해야 하는 것

1. **사용자가 친 글자를 저장해도 된다는 판단은 우리 해석입니다.** 카카오에
   물어본 적이 없습니다. 근거는 "그 글자는 카카오 응답이 아니라 사용자 입력"이라는
   것인데, 이 해석이 틀릴 가능성은 낮지만 0은 아닙니다.
2. **장소 이름 검색이 "실시간 호출로만 이용 가능"이라는 규칙의 적용 대상인지
   확인하지 않았습니다.** 같은 로컬 API 묶음이므로 같은 규칙일 것으로 보고
   설계했습니다. 어차피 이 설계는 검색 결과를 저장하지 않으므로 규칙이 같든
   다르든 어긋나지 않습니다.
3. **상위 결과에 원하는 자리가 있다는 것은 검색어 일곱 개에서만 확인했습니다.**
   `경주`와 `애월`에서 두 번째였다는 것이 모든 검색어에 통한다는 뜻은 아닙니다.
   특히 카카오의 순위 규칙은 공개되어 있지 않아 시간이 지나면 달라질 수 있습니다.
4. **`더 보기`가 자동으로 이어 붙이는 방식보다 낫다는 것은 사용자 조사로 확인한
   것이 아닙니다.** 근거는 이 저장소가 이미 같은 모양의 단추를 쓰고 있다는
   일관성과, 화면 낭독기 사용자에게 알리는 장치를 따로 만들지 않아도 된다는
   것입니다.
5. **위치 권한을 거부한 사람이 실제로 이 길로 돌아오는지 셀 수 없습니다.**
   이 서비스에는 계측이 없고 서버 저장소도 로그인도 없어서, 2절에서 말한 두
   번째 이유가 실제로 얼마나 큰지 측정할 방법이 없습니다.
6. **`경주 황리단길 주변`처럼 표시하는 문구가 길어지는 경우를 재지 않았습니다.**
   장소 이름이 긴 곳(예: `해운대블루라인파크 청사포정거장`)에서 한 줄에 들어가지
   않을 수 있습니다. 구현하면서 줄임 규칙을 정해야 합니다.

## 7. 완료 조건

- [ ] 위치 권한을 거부한 상태에서도 `다른 곳에서 찾기`로 결과 화면까지 닿는다 —
      브라우저에서 위치 권한을 차단한 채 검색으로 조회해 확인
- [ ] `경주`를 검색하면 열다섯 곳이 나오고, `더 보기`를 누르면 목록이 늘어나며,
      카카오가 끝을 알리면 단추가 사라지고 더 좁혀 찾으라는 안내가 뜬다
- [ ] 45곳을 못 채우는 검색어에서도 마지막 페이지에서 단추가 사라진다 —
      `강남역`(34곳)으로 확인. 페이지 수를 코드에 적지 않고 `is_end`를 읽는지
      함께 확인
- [ ] 마지막 페이지를 넘겨 요청해도 같은 항목이 목록에 쌓이지 않는다 —
      3-3절의 함정. 가짜 카카오 서버가 같은 페이지를 반복해서 주도록 두고 확인
- [ ] 후보·결과 화면에 기준 위치가 표시되고, 브라우저 위치일 때와 옮긴 위치일 때
      문구가 다르다
- [ ] 결과 화면의 `← 후보 다시 보기`를 누르면 옮긴 위치 그대로 후보 화면으로
      돌아가고 `다시 뽑기`가 동작한다
- [ ] 빈 결과 화면의 `다시 찾아보기`가 **옮긴 위치의 좌표로** 반경을 넓혀 다시
      찾는다(사용자가 서 있는 자리로 되돌아가지 않는다) — 4-7절의 함정
- [ ] 브라우저 저장소에 남는 것이 사용자가 친 글자뿐이다 — 개발자 도구에서
      `random-choice.keyword.v1`을 열어 좌표와 장소 이름이 없음을 확인
- [ ] 새 서버 경로가 비밀값 헤더 없이는 거부된다 — 헤더 없이 `/api/v1/places`를
      불러 401이 오는 것을 확인
- [ ] `README.md`가 지금 상태와 맞는다 — 화면 그림에 위치 검색 화면이 들어가고,
      시작 단추 이름이 `위치 허용하고 시작하기`에서 바뀐 것이 반영되고,
      브라우저에 남기는 것 목록에 사용자가 친 글자가 더해지고, "아직 없는 것들"에서
      "주소를 직접 입력해 위치 지정"이 빠진 것을 확인
- [ ] `just check`가 통과한다(서버 시험·검사, 화면 빌드·시험·타입·린트)

## 8. 어떻게 시험하는가

- **가짜 카카오 서버**로 장소 검색 경로를 시험합니다. 지금 음식점 조회를
  시험하는 방식과 같은 패턴입니다. 특히 `is_end`가 참일 때 더 요청하지 않는지,
  마지막 페이지가 반복되어 와도 목록에 중복이 쌓이지 않는지를 확인합니다.
- **`web/lib/anchor.ts`**는 저장소를 밖에서 받는 순수 함수이므로
  `web/lib/visits.test.ts`와 같은 방식으로 가짜 저장소를 넣어 시험합니다.
- **화면 시험**은 브라우저 없이 돌므로(`web/vitest.config.mts`) 판단이 들어가는
  코드를 `lib/` 아래에 두고 그곳을 시험합니다. `app/`과 `components/`에는
  판단을 두지 않습니다.
- **실제 카카오 응답으로 하는 확인**은 개발자가 손으로 한 번 재현합니다.
  자동화된 시험으로 만들지 않습니다. 카카오 응답이 매번 조금씩 바뀔 수 있어
  고정된 기대값을 둘 수 없기 때문입니다.
